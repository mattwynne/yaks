# Goal

Reject `yx blocker add` commands that would introduce a cycle in the effective blocker graph.

# Effective Graph Rules

- `yx blocker add A --by B` means `B` blocks `A`; model it as edge `B → A`.
- Hierarchy is an implicit blocker edge from descendant to ancestor: child/descendant blocks parent/ancestor.
- Active explicit blockers plus implicit hierarchy blockers form the effective blocking graph.
- The effective graph must remain acyclic.
- Failed adds emit no `BlockerAdded` or `BlockerUpdated` events.

# Rules / Examples

```gherkin
Scenario: Self-blocking is rejected
  Given I have a clean git repository
  And I add the yak "deploy"
  When I try to run yx blocker add deploy --by deploy
  Then the command should fail
  And the error should explain that a yak cannot block itself
  And the log should not include a BlockerAdded event
```

```gherkin
Scenario: Mutual explicit cycle is rejected
  Given I have a clean git repository
  And I add the yak "A"
  And I add the yak "B"
  And I run yx blocker add A --by B
  When I try to run yx blocker add B --by A
  Then the command should fail
  And the error should mention a blocker cycle involving "A" and "B"
  And the log should not include a BlockerAdded event for "B" blocked by "A"
```

```gherkin
Scenario: Longer explicit cycle is rejected
  Given yaks "A", "B", and "C" exist
  And I run yx blocker add A --by B
  And I run yx blocker add B --by C
  When I try to run yx blocker add C --by A
  Then the command should fail
  And the error should mention the dependency path "A", "B", and "C"
  And no blocker event should be emitted for the rejected add
```

```gherkin
Scenario: Hierarchy plus explicit cycle is rejected
  Given I have a clean git repository
  And I add the yak "parent"
  And I add the yak "child" under "parent"
  When I try to run yx blocker add child --by parent
  Then the command should fail
  And the error should explain that the hierarchy already makes "child" block "parent"
  And no blocker event should be emitted
```

```gherkin
Scenario: Multi-ancestor hierarchy plus explicit cycle is rejected
  Given I have a clean git repository
  And I add the yak "parent"
  And I add the yak "child" under "parent"
  And I add the yak "grandchild" under "child"
  When I try to run yx blocker add grandchild --by parent
  Then the command should fail
  And the error should mention the hierarchy path from "grandchild" to "parent"
  And no blocker event should be emitted
```

# Acceptance Notes

- Cycle detection must consider both explicit blockers and hierarchy blockers.
- Redundant hierarchy blocker in the safe direction (`child → parent`) belongs in `make blocker commands idempotent with advice`; keep that as a no-op success, not an error.
- Error messages should be actionable: mention that the command would create a cycle and include the relevant yak names/path.
- Exact wording can evolve; tests should assert key facts.

# Test Guidance

Prefer Gherkin scenarios for CLI behaviour and event-log assertions. Add domain/unit tests for the graph/path checker, especially longer paths and mixed hierarchy/explicit edges.
