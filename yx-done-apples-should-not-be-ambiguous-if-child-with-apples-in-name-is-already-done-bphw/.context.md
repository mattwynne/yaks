# Goal
State-changing commands should ignore yaks that are already in the target state when resolving fuzzy names.

# Problem
A command like `yx done apples` can be ambiguous if both a not-done yak and an already-done child/sibling match "apples". The already-done yak is irrelevant because applying the command to it would be a no-op, so it should not cause ambiguity.

# Desired Behaviour
For `yx state <name> <target-state>` and aliases such as `yx done` / `yx start`:

- Resolve fuzzy matches against yaks that are **not already in the target state** first.
- If exactly one non-target-state yak matches, use it.
- If multiple non-target-state yaks match, report ambiguity as today.
- If no non-target-state yaks match but one or more already-target-state yaks match, report that the matching yak(s) are already in that state rather than treating them as actionable ambiguity.
- If nothing matches at all, report not found as today.

# Example
Given:

- `apples` is todo
- `shopping/buy apples` is done

Then:

```bash
yx done apples
```

should mark `apples` done, not fail as ambiguous because `shopping/buy apples` is already done.

# Scope
Generalise this for all target states (`todo`, `wip`, `blocked`, `done`) and state aliases (`done`, `start`).
