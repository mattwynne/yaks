# Read YakStore from git tree, not filesystem projection

## What changed

**ADR 0019 (Event-source the aggregate):** The `YakMap` aggregate now
loads by replaying events via `from_events()`. It no longer calls
`ReadYakStore` at all for command-side state. This eliminates the
original motivation around aggregate correctness.

**ADR 0018 (Unify Yak types):** `YakSnapshot` is now just a type alias
for `Yak`. The "reconcile tags in YakSnapshot with YakView" child yak
is obsolete in its original framing — there's only one type now.

## Remaining motivation

`ReadYakStore` is still used for **queries only**:
- `get_yak()` — used by `yx show`, `yx context --show`, `yx field --show`
- `list_yaks()` — used by `yx ls`, tab completions, building children lists
- `fuzzy_find_yak_id()` — used by most commands to resolve names to IDs
- `read_field()` — used by `yx field --show`

These all read from the `.yaks/` filesystem projection. If the projection
has a bug, queries return wrong data even though the event log and aggregate
are correct. This is a cosmetic rather than data-corruption issue (events
are safe), but it's still confusing for users.

## Tags gap in git tree

`read_snapshots_from_tree()` currently sets `tags: vec![]` because the
git tree doesn't store tags separately — they're written via
`FieldUpdated` events with field name `.tags`. The `Compacted` event
builder also doesn't write tags to the tree (it calls
`YakSubtreeBuilder::custom_fields()` which only writes from `yak.fields`,
not `yak.tags`).

This means tags are lost when reading from the git tree (reset, compact).
This is a real bug that exists regardless of this yak's scope.

## Revised scope

The original plan had 6 steps. Steps 5 (switch aggregate) is done via
event sourcing. The remaining value is:

1. **Fix the tags gap** — ensure tags survive compaction and tree reads
   (this is a bug fix, could be a separate yak)
2. **Split contract tests** — still useful if we want a read-only adapter
3. **Create `GitTreeReadYakStore`** — implement `ReadYakStore` backed by
   the git tree at `refs/notes/yaks`
4. **Wire it in** — queries read from git tree instead of `.yaks/`
5. **Demote `.yaks/` to write-only** — human-readable projection only

## Open question

Is this still worth doing? The aggregate is now safe. The `.yaks/`
projection is updated synchronously and has been reliable in practice.
The main benefits would be:
- Eliminating a class of potential projection bugs on the query side
- Removing the dependency on `.yaks/` being correct for reads
- Simplifying `yx reset` (no longer needed to fix query-side state)

The main cost is performance — reading from the git tree on every query
is slower than reading from the filesystem.

Consider whether the tags bug fix should be extracted as a standalone yak.
