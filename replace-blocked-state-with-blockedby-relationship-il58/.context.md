# Goal

Replace the stored `blocked` workflow state with explicit blocker relationships, while keeping workflow state focused on direct work.

# Next Yak

Start with `vertical slice explicit blockers affect readiness`.

That child yak is the first implementation slice and should be picked up before the other children.

# Forward Model

- Stored workflow state: `todo | wip | done`
- Derived readiness: `ready = state == todo && no unresolved blockers`
- Blockers come from two sources:
  - implicit hierarchy blockers: incomplete children/descendants block ancestors
  - explicit blocker events: active `BlockerAdded` relationships
- Parent/child hierarchy is not stored as explicit blocker events; it remains hierarchy.
- Parent progress is presentation/roll-up, not stored parent state.

# Event-Sourced Model

Source of truth is the event stream.

Commands/events:

- `yx blocker add <yak> --by <blocker> [--reason <reason>]`
  - emits `BlockerAdded(target, blocker, reason?)` when the blocker is new
  - emits `BlockerUpdated(target, blocker, reason?)` when the active blocker exists and the reason changes
  - `--reason ""` clears an existing reason via `BlockerUpdated(target, blocker, None)`
- `yx blocker rm <yak> --by <blocker>` emits `BlockerRemoved(target, blocker)`
- `yx blocker remove` is an alias for `rm`
- Marking a blocker yak `done` emits `BlockerRemoved(target, blocker)` for each active explicit relationship resolved by that completion

The current `blocked_by` view/projection is derived by replaying `BlockerAdded`, `BlockerUpdated`, and `BlockerRemoved` events.

# Design Decisions

## Public concepts

- Keep one public derived status: `ready`.
- Do not introduce `available` in this slice.
- `yx list --ready` means “things you can start next”.
- WIP yaks are not ready, even if unblocked.
- WIP yaks can still have explicit blockers shown via `blocked_by`.

## Starting yaks

- `yx start <yak>` should only be allowed when the yak is ready.
- Starting a yak with unresolved explicit blockers fails clearly and emits no state event.
- Starting a parent with incomplete children fails clearly and emits no state event.
- An override such as `--remove-blockers` is not part of the first vertical slice unless deliberately added with Gherkin coverage.

## JSON/show views

- Add `blocked_by` to `yx list --format json` and `yx show --format json`.
- Include explicit blockers only, each with:
  - `id`
  - `name`
  - `state`
  - optional `reason`
- Do not duplicate implicit child blockers in `blocked_by`; hierarchy remains represented by `children`/breadcrumbs.
- Keep `ready` as the derived field combining workflow state, hierarchy blockers, and explicit blockers.

## Duplicate and redundant adds

- Adding an already-active explicit blocker with no effective change is a no-op success, emits no event, and prints advice.
- Adding an explicit blocker already implied by hierarchy is a no-op success, emits no event, and prints advice.
- Adding an existing blocker with a changed reason emits `BlockerUpdated`.

## Hierarchy vs explicit blockers

- `yx add/mv --blocks` remains hierarchy language.
- Hierarchy creates implicit blocking for readiness but does not emit `BlockerAdded`.
- `yx blocker add --by` creates an explicit relationship without moving either yak.

## No cycles

Cycles are not allowed in the effective blocking graph.

The effective graph includes:

- implicit hierarchy blockers
- active explicit blockers

Adding a blocker or moving a yak must be rejected if it would introduce any cycle, including:

- self-cycles
- mutual explicit cycles
- longer explicit cycles
- hierarchy + explicit cycles
- multi-ancestor blocking cycles

# Acceptance Test Requirements

Use Gherkin for user-visible behaviour. The first vertical slice should cover:

- explicit blocker makes a yak not ready
- explicit blocker appears in JSON with optional reason
- `yx list --ready` excludes blocked yaks
- completing a blocker emits `BlockerRemoved` and can make the target ready
- manual blocker removal emits `BlockerRemoved`
- changing/clearing a reason emits `BlockerUpdated`
- duplicate/redundant adds are no-op successes with advice and no events
- hierarchy blockers are distinct from explicit `blocked_by`
- start fails for non-ready yaks

# Test Guidance

- Prefer Gherkin scenarios in `features/` for user-visible behaviour.
- Keep focused unit tests for domain invariants and graph validation.
- Assert machine-readable JSON or explicit command output where possible.
- Avoid adding richer human UI/glyph changes in this slice.
