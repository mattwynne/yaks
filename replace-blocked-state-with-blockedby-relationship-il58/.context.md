# Goal

Explore replacing the `blocked` workflow state with explicit blocker relationships.

# Desired Model

A yak can have intrinsic workflow state plus unresolved blockers:

- workflow_state: `todo | wip | done`
- blocked_by: yak IDs / relationships

This should support a yak being blocked regardless of whether it is todo or wip.

# Design Decisions

- User-facing command language: `yx block <yak> --by <blocker>`.
- Provide a matching unblock operation, likely `yx unblock <yak> --by <blocker>` unless later design changes this.
- Parent/child hierarchy remains distinct from explicit `blocked_by` storage:
  - `yx add/mv --blocks` is hierarchy language.
  - hierarchy creates an implicit blocking relationship for readiness, but should not be recorded redundantly in explicit `blocked_by` state.
  - explicit `yx block --by` creates a blocker relationship without moving either yak.
- Cycles are not allowed in the effective blocking graph.
  - The effective graph includes both implicit hierarchy blockers and explicit `blocked_by` relationships.
  - Children implicitly block ancestors/parents for readiness.
  - Explicit blockers block their target yak.
  - Adding an explicit blocker or moving a yak must be rejected if it would introduce any cycle.
  - This includes self-cycles, mutual cycles, longer cycles, hierarchy+explicit cycles, and multi-ancestor blocking cycles.

# Example Mapping Needed Before Implementation

Use example mapping before coding this yak. Be thorough, especially around cycles and moves.

## Cycle Examples to Map

- Self-blocking:
  - Given `A`
  - When `yx block A --by A`
  - Then it fails.
- Mutual explicit cycle:
  - Given `A` is blocked by `B`
  - When `yx block B --by A`
  - Then it fails.
- Longer explicit cycle:
  - Given `A` is blocked by `B`, and `B` is blocked by `C`
  - When `yx block C --by A`
  - Then it fails.
- Child blocks parent implicitly, so parent cannot explicitly block child:
  - Given `child` is under `parent`
  - Then `child` already blocks `parent` implicitly.
  - When `yx block child --by parent`
  - Then it fails because it creates an effective cycle.
- Multi-ancestor blocking:
  - Given `grandchild` is under `child`, and `child` is under `parent`
  - Then `grandchild` implicitly blocks both `child` and `parent` through ancestry/readiness.
  - When `yx block grandchild --by parent`
  - Then it fails because it creates an effective cycle.
- Redundant explicit blocker:
  - Given `child` is under `parent`
  - When `yx block parent --by child`
  - Decide whether this is rejected as redundant or accepted as a no-op, but it must not create duplicate explicit state for the implicit hierarchy blocker.

## Move Examples to Map

Moving yaks can create cycles in the effective graph and must be validated too.

- Moving a yak under one of its descendants is already invalid and should remain invalid.
- Moving a blocker under the yak it blocks:
  - Given `A` is blocked by `B`
  - When moving `B` under `A`
  - Then it would make `B` implicitly block `A` via hierarchy while `B` is inside `A`; map whether/how this creates an effective cycle and reject if so.
- Moving a blocked yak under its blocker:
  - Given `A` is blocked by `B`
  - When moving `A` under `B`
  - Then check whether the combined graph remains acyclic; document expected behaviour.
- Moving subtrees with blockers pointing into/out of the subtree:
  - Given `A` has descendants and explicit blockers outside the subtree
  - When moving `A`, validate the full effective graph after the move.
- Moving a yak so that an ancestor becomes an explicit blocker of its descendant:
  - Any move that makes an existing explicit blocker become an ancestor/descendant relationship must be checked for cycles.

# Design Work Needed Before Implementation

The explicit blocker model needs careful example mapping before coding. Explore edge cases with concrete examples, especially:

- circular dependencies
  - self-blocking
  - mutual blocking between two yaks
  - longer cycles through explicit blockers
  - cycles involving hierarchy plus explicit blockers
- moving yaks that participate in blocker relationships
  - moving a yak that is blocked by another yak
  - moving a yak that blocks other yaks
  - moving parent/child subtrees where explicit blockers point into or out of the subtree
  - whether any move can create an invalid implicit+explicit cycle
- deletion/removal/pruning
  - removing a blocker yak
  - pruning a done blocker yak
  - removing a yak that is blocked by others
- completion/readiness semantics
  - parent implicit blockers and explicit blockers compose, but remain represented separately
  - explicit blockers should not duplicate children in `blocked_by`

# Acceptance / BDD Requirements

This yak should include feature-level Gherkin coverage, not just unit tests. Add or update scenarios that describe the behaviour users rely on.

Suggested feature coverage:

- A yak can be blocked by another yak explicitly.
  - Given yak `deploy` and yak `fix bug`
  - When `deploy` is blocked by `fix bug` using `yx block deploy --by "fix bug"`
  - Then `deploy` is not ready
  - And JSON/list output exposes the blocker relationship clearly.
- A blocked yak becomes ready when all explicit blockers are done.
  - Given `deploy` is blocked by `fix bug`
  - When `fix bug` is marked done
  - Then `deploy` appears in `yx list --ready` if its workflow state is otherwise actionable.
- A yak can be `wip` and still blocked.
  - This is the key distinction from the old single `blocked` state.
- Parent/child readiness and explicit blocker readiness compose.
  - A parent is only ready when children are complete and explicit blockers are resolved.
- Existing completion/status filters stay clear:
  - `yx list --only not-done` remains workflow-state based.
  - `yx list --ready` remains availability/readiness based.
- Cycles or invalid blockers are rejected with clear errors.
  - A yak cannot block itself.
  - Mutual/cyclic blocking should be rejected in the combined implicit+explicit blocking graph.
- Hierarchy and explicit blockers remain distinct.
  - `yx mv child --blocks parent` changes hierarchy and implicitly affects parent readiness.
  - It does not add an explicit `blocked_by` entry.
- Moves validate the resulting effective blocking graph.
  - Any move that would create a cycle through existing explicit blockers plus hierarchy must fail.

# Test Guidance

- Prefer Gherkin scenarios in `features/` for user-visible behaviour.
- Keep focused unit tests for domain invariants and edge cases.
- Ensure scenario language distinguishes stored workflow state from derived readiness/availability.
- Avoid relying only on glyphs/colors; assert machine-readable JSON or explicit command output where possible.
