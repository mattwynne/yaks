# Goal

Explore replacing the `blocked` workflow state with explicit blocker relationships.

# Desired Model

A yak can have intrinsic workflow state plus unresolved blockers:

- workflow_state: `todo | wip | done`
- blocked_by: yak IDs / relationships

This should support a yak being blocked regardless of whether it is todo or wip.

# Event-Sourced Model

Source of truth is the event stream. Talk about blocker changes as commands and events, not as direct mutation of a stored list.

Commands/events:

- `yx blocker add <yak> --by <blocker> [--reason <reason>]` emits `BlockerAdded(target, blocker, reason?)` when the blocker is new.
- `yx blocker add <yak> --by <blocker> --reason <reason>` emits `BlockerUpdated(target, blocker, reason?)` when the blocker already exists and the reason changes.
- `yx blocker add <yak> --by <blocker> --reason ""` clears an existing reason by emitting `BlockerUpdated(target, blocker, None)`.
- `yx blocker rm <yak> --by <blocker>` emits `BlockerRemoved(target, blocker)`.
- `yx blocker remove <yak> --by <blocker>` is an alias for `rm`.
- Marking a blocker yak `done` must emit `BlockerRemoved(target, blocker)` events for each active explicit blocker relationship resolved by that completion.
- The current `blocked_by` view/projection is derived by replaying `BlockerAdded`, `BlockerUpdated`, and `BlockerRemoved` events.

# Design Decisions

- User-facing command language: `yx blocker add <yak> --by <blocker> [--reason <reason>]` and `yx blocker rm|remove <yak> --by <blocker>`.
- Manual blocker removal is supported. Removing an active blocker emits `BlockerRemoved(target, blocker)`, even if the blocker yak is not done.
- Event names: `BlockerAdded`, `BlockerUpdated`, and `BlockerRemoved`.
- Optional blocker reason:
  - `--reason` is accepted on `blocker add`.
  - New blocker with reason emits `BlockerAdded(target, blocker, reason)`.
  - Existing blocker with changed reason emits `BlockerUpdated(target, blocker, reason)`.
  - Existing blocker with `--reason ""` clears the reason via `BlockerUpdated(target, blocker, None)`.
  - Existing blocker with same/no effective reason remains a no-op success with advice and no event.
- JSON/show views expose explicit blockers only:
  - Add `blocked_by` array to `yx list --format json` and `yx show --format json`.
  - Each explicit blocker should include `id`, `name`, `state`, and optional `reason`.
  - Do not include child/ancestor implicit blockers in `blocked_by`; hierarchy remains represented by `children`/breadcrumbs.
  - Keep `ready` as the overall derived availability field combining workflow state, hierarchy, and explicit blockers.
- Duplicate/redundant blocker adds:
  - Adding an already-active explicit blocker with no effective change is a no-op success and emits no event.
  - Adding an explicit blocker that is already implied by hierarchy is a no-op success and emits no event.
  - In both cases, print advice explaining that the command was unnecessary.
- Parent/child hierarchy remains distinct from explicit blocker events:
  - `yx add/mv --blocks` is hierarchy language.
  - hierarchy creates an implicit blocking relationship for readiness, but should not emit `BlockerAdded` or be recorded redundantly as explicit `blocked_by` state.
  - explicit `yx blocker add --by` creates a blocker relationship without moving either yak.
- Cycles are not allowed in the effective blocking graph.
  - The effective graph includes both implicit hierarchy blockers and explicit `blocked_by` relationships.
  - Children implicitly block ancestors/parents for readiness.
  - Explicit blockers block their target yak.
  - Adding an explicit blocker or moving a yak must be rejected if it would introduce any cycle.
  - This includes self-cycles, mutual cycles, longer cycles, hierarchy+explicit cycles, and multi-ancestor blocking cycles.
- Explicit blocker relationships represent active blockers only in the current projection.
  - When a blocker yak is marked `done`, emit `BlockerRemoved` for each active explicit relationship involving that blocker.
  - History is preserved by blocker events in the event log/version control.

# Example Mapping Needed Before Implementation

Use example mapping before coding this yak. Be thorough, especially around cycles and moves.

## JSON / View Examples to Map

- Explicit blockers in JSON:
  - Given `deploy` is explicitly blocked by `fix bug` with reason `crashes in staging`
  - When I run `yx show --format json deploy` or `yx list --format json`
  - Then `deploy.blocked_by` includes `{ id, name: "fix bug", state, reason: "crashes in staging" }`.
- Implicit hierarchy blockers are not duplicated in `blocked_by`:
  - Given `fix bug` is a child of `deploy`
  - When I show/list JSON for `deploy`
  - Then `fix bug` appears under `children`
  - And `deploy.blocked_by` does not include `fix bug` unless there is also an active explicit blocker event, which should generally be avoided as redundant.
- Overall readiness composes both sources:
  - Given `deploy` has incomplete children or active explicit blockers
  - Then `deploy.ready` is false.

## Duplicate / Redundant Examples to Map

- Duplicate explicit blocker:
  - Given `BlockerAdded(deploy, fix-bug)` has been applied
  - When `yx blocker add deploy --by "fix bug"`
  - Then it succeeds, emits no event, and advises that the blocker already exists.
- Duplicate explicit blocker with a changed reason:
  - Given `BlockerAdded(deploy, fix-bug, None)` has been applied
  - When `yx blocker add deploy --by "fix bug" --reason "crashes in staging"`
  - Then it emits `BlockerUpdated(deploy, fix-bug, "crashes in staging")`.
- Duplicate explicit blocker with the same reason:
  - Given `BlockerAdded(deploy, fix-bug, "crashes in staging")` has been applied
  - When `yx blocker add deploy --by "fix bug" --reason "crashes in staging"`
  - Then it succeeds, emits no event, and advises that nothing changed.
- Redundant hierarchy blocker:
  - Given `fix bug` is a child of `deploy`
  - When `yx blocker add deploy --by "fix bug"`
  - Then it succeeds, emits no event, and advises that `fix bug` already blocks `deploy` through hierarchy.

## Cycle Examples to Map

- Self-blocking:
  - Given `A`
  - When `yx blocker add A --by A`
  - Then it fails and emits no event.
- Mutual explicit cycle:
  - Given `BlockerAdded(A, B)` has been applied
  - When `yx blocker add B --by A`
  - Then it fails and emits no event.
- Longer explicit cycle:
  - Given `BlockerAdded(A, B)` and `BlockerAdded(B, C)` have been applied
  - When `yx blocker add C --by A`
  - Then it fails and emits no event.
- Child blocks parent implicitly, so parent cannot explicitly block child:
  - Given `child` is under `parent`
  - Then `child` already blocks `parent` implicitly.
  - When `yx blocker add child --by parent`
  - Then it fails because it creates an effective cycle and emits no event.
- Multi-ancestor blocking:
  - Given `grandchild` is under `child`, and `child` is under `parent`
  - Then `grandchild` implicitly blocks both `child` and `parent` through ancestry/readiness.
  - When `yx blocker add grandchild --by parent`
  - Then it fails because it creates an effective cycle and emits no event.
- Redundant explicit blocker:
  - Given `child` is under `parent`
  - When `yx blocker add parent --by child`
  - Then it succeeds as a no-op with advice and emits no event because hierarchy already supplies that blocker.

## Move Examples to Map

Moving yaks can create cycles in the effective graph and must be validated too.

- Moving a yak under one of its descendants is already invalid and should remain invalid.
- Moving a blocker under the yak it blocks:
  - Given `BlockerAdded(A, B)` has been applied
  - When moving `B` under `A`
  - Then it would make `B` implicitly block `A` via hierarchy while `B` is inside `A`; map whether/how this creates an effective cycle and reject if so.
- Moving a blocked yak under its blocker:
  - Given `BlockerAdded(A, B)` has been applied
  - When moving `A` under `B`
  - Then check whether the combined graph remains acyclic; document expected behaviour.
- Moving subtrees with blockers pointing into/out of the subtree:
  - Given `A` has descendants and explicit blockers outside the subtree
  - When moving `A`, validate the full effective graph after the move.
- Moving a yak so that an ancestor becomes an explicit blocker of its descendant:
  - Any move that makes an existing explicit blocker become an ancestor/descendant relationship must be checked for cycles.

## Completion / Resolution Examples to Map

- Completing a blocker removes active explicit blocker relationships:
  - Given `BlockerAdded(deploy, fix-bug)` has been applied
  - When `fix-bug` is marked done
  - Then the command emits `FieldUpdated(fix-bug, .state=done)` and `BlockerRemoved(deploy, fix-bug)`
  - And `deploy` may become ready if no other blockers remain and its workflow state/children permit it.
- Completing one of several blockers removes only that blocker:
  - Given `BlockerAdded(deploy, fix-bug)` and `BlockerAdded(deploy, write-docs)` have been applied
  - When `fix-bug` is marked done
  - Then the command emits `BlockerRemoved(deploy, fix-bug)` only.
  - And `deploy` is still blocked by `write-docs`.
- Manually removing a blocker:
  - Given `BlockerAdded(deploy, fix-bug)` has been applied
  - When `yx blocker rm deploy --by "fix bug"`
  - Then the command emits `BlockerRemoved(deploy, fix-bug)`
  - And `deploy` may become ready even though `fix-bug` is not done.

## Reason Examples to Map

- Adding a blocker with a reason:
  - When `yx blocker add deploy --by "fix bug" --reason "crashes in staging"`
  - Then `BlockerAdded(deploy, fix-bug, "crashes in staging")` is emitted.
  - And JSON/show output exposes the reason while the blocker is active.
- Adding a blocker without a reason:
  - Then `BlockerAdded(deploy, fix-bug, None)` is emitted/represented.
- Updating a reason:
  - Given `BlockerAdded(deploy, fix-bug, None)` has been applied
  - When `yx blocker add deploy --by "fix bug" --reason "crashes in staging"`
  - Then `BlockerUpdated(deploy, fix-bug, "crashes in staging")` is emitted.
- Clearing a reason:
  - Given `BlockerAdded(deploy, fix-bug, "crashes in staging")` has been applied
  - When `yx blocker add deploy --by "fix bug" --reason ""`
  - Then `BlockerUpdated(deploy, fix-bug, None)` is emitted.

# Design Work Needed Before Implementation

The explicit blocker model needs careful example mapping before coding. Explore edge cases with concrete examples, especially:

- circular dependencies
  - self-blocking
  - mutual blocking between two yaks
  - longer cycles through explicit blockers
  - cycles involving hierarchy plus explicit blockers
- moving yaks that participate in blocker relationships
  - moving a yak that is blocked by another yak
  - moving a yak that blocks other yaks
  - moving parent/child subtrees where explicit blockers point into or out of the subtree
  - whether any move can create an invalid implicit+explicit cycle
- deletion/removal/pruning
  - removing a blocker yak
  - pruning a done blocker yak
  - removing a yak that is blocked by others
- completion/readiness semantics
  - parent implicit blockers and explicit blockers compose, but remain represented separately
  - explicit blockers should not duplicate children in `blocked_by`
  - explicit blockers are active-only in the current projection and are resolved with `BlockerRemoved` events

This yak should include feature-level Gherkin coverage, not just unit tests. Add or update scenarios that describe the behaviour users rely on.

Suggested feature coverage:

- A yak can be blocked by another yak explicitly.
  - Given yak `deploy` and yak `fix bug`
  - When `deploy` is blocked by `fix bug` using `yx blocker add deploy --by "fix bug"`
  - Then `deploy` is not ready
  - And JSON/list output exposes the blocker relationship clearly.
  - And the log includes a `BlockerAdded` event/narrative.
- A blocker can be manually removed.
  - Given `deploy` is blocked by `fix bug`
  - When I run `yx blocker rm deploy --by "fix bug"`
  - Then a `BlockerRemoved(deploy, fix bug)` event is emitted
  - And `deploy` may become ready even if `fix bug` is not done.
- A blocker can have an optional reason.
  - Given yak `deploy` and yak `fix bug`
  - When I run `yx blocker add deploy --by "fix bug" --reason "crashes in staging"`
  - Then the active blocker shown in JSON/show includes that reason.
- Adding/changing/clearing a reason on an existing blocker emits `BlockerUpdated`.
- A blocked yak becomes ready when all explicit blockers are done.
  - Given `deploy` is blocked by `fix bug`
  - When `fix bug` is marked done
  - Then a `BlockerRemoved(deploy, fix bug)` event is emitted
  - And `deploy` no longer has `fix bug` in explicit `blocked_by`
  - And `deploy` appears in `yx list --ready` if its workflow state is otherwise actionable.
- A yak can be `wip` and still blocked.
  - This is the key distinction from the old single `blocked` state.
- Parent/child readiness and explicit blocker readiness compose.
  - A parent is only ready when children are complete and explicit blockers are resolved.
- Existing completion/status filters stay clear:
  - `yx list --only not-done` remains workflow-state based.
  - `yx list --ready` remains availability/readiness based.
- Duplicate/redundant blocker adds are no-op successes with advice and no events unless the reason changes, in which case `BlockerUpdated` is emitted.
- Cycles or invalid blockers are rejected with clear errors.
  - A yak cannot block itself.
  - Mutual/cyclic blocking should be rejected in the combined implicit+explicit blocking graph.
- Hierarchy and explicit blockers remain distinct.
  - `yx mv child --blocks parent` changes hierarchy and implicitly affects parent readiness.
  - It does not emit `BlockerAdded`.
- Moves validate the resulting effective blocking graph.
  - Any move that would create a cycle through existing explicit blockers plus hierarchy must fail.
