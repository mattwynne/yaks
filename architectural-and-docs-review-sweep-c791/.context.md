## Finding 1: Explicit blockers may be lost by compaction

Severity: high.

Raised by: Codex. Verified against current code shape.

Evidence:

- `src/domain/event.rs` defines `YakEvent::Compacted(Vec<Yak>, Vec<YakId>, EventMetadata)` with no blocker snapshot data.
- `src/domain/yak_map.rs` `apply_compacted` clears `self.blockers` and restores only yak snapshots plus manual blocker compatibility fields.
- `src/adapters/event_store/tree.rs` treats blocker events as preserving the current tree; compaction rebuilds only from snapshots.
- `src/adapters/event_store/memory.rs` ignores blocker events in snapshot building and compacted replay restores only yaks.
- `features/compact.feature` has no scenario for explicit blocker preservation through `yx compact`.

Concern:

After compaction, an explicitly blocked yak may become ready/unblocked even though no user removed the blocker.

Decision: fix with a proper aggregate snapshot.

Create/implement child yak `compact whole YakMap snapshot`. Compaction should snapshot the whole `YakMap` aggregate state, not just `Vec<Yak>`, by introducing an explicit `YakMapSnapshot`-style type that includes yaks, removed IDs, active explicit blockers, and manual blockers.

Acceptance should start with a failing scenario: add explicit blocker, compact, JSON still shows `blocked_by`, target remains `ready: false`.

## Finding 2: `active` vs `explicit` blocker terminology is muddy

Severity: medium.

Raised by: Claude.

Evidence:

- `features/blockers.feature` uses phrases like `active explicit blocker`.
- `src/domain/yak_map.rs` defines `ActiveBlocker` and `active_blockers()`.
- `active_blockers()` includes current explicit blockers plus manual blockers. Done/removed blocker relationships are cleaned up as side effects, so "active" means currently unresolved relationship, while "explicit" means user-created yak-to-yak relationship.

Concern:

The implementation works, but terminology increases cognitive load. Domain docs should make the distinction clear, and feature titles could be simpler.

Decision: model cleanup via child yak `unify blocker domain model and events`.

Manual blockers and yak-to-yak blockers should be represented by one coherent `Blocker` model with a `BlockerSource` such as `Yak(YakId)` or `Manual`. The current `ActiveBlocker` view and split `blockers` / `manual_blockers` maps are symptoms of the model being split.

Also unify events around `BlockerAdded/Updated/Removed` with explicit source kind, while preserving replay compatibility for existing split manual blocker events. This should resolve or rename `ActiveBlocker` as part of the design.

## Finding 3: Feature examples are precise but not very domainful

Severity: low/medium.

Raised by: Codex and Claude.

Evidence:

- `features/blockers.feature` repeatedly uses role-placeholder names like `blocked yak` and `blocking yak`.

Concern:

Role names are precise for edge cases, but the first happy-path scenario may communicate domain intent better with examples like `deploy release` blocked by `security review`.

Decision: create/implement child yak `make blocker feature examples vivid`.

Use vivid, domainful examples instead of abstract placeholders where this improves executable documentation. Avoid names like `blocked yak`, `blocking yak`, `a`, `b`, `c` unless abstraction is genuinely clearer for a graph-shape case. This is wording/test-data cleanup, not behaviour change.

## Finding 4: `path_to_blocker` returns a boolean flag for path kind

Severity: low.

Raised by: Claude.

Evidence:

- `src/domain/yak_map.rs` `path_to_blocker` returns `Option<(Vec<YakId>, bool)>`.
- Call sites interpret the boolean as `uses_hierarchy`.

Concern:

A small enum such as `BlockerPathKind::{ExplicitOnly, UsesHierarchy}` would express intent better than a boolean.

Decision: resolved by child yak `unify blocker domain model and events`.

The tuple/boolean path modelling was replaced by named `BlockerPath`, which makes the path intent explicit. We deliberately did not expose a separate hierarchy-kind enum because there is no current user-facing need for that distinction; hierarchy remains an internal explanation detail.

## Finding 5: Step/domain parameter order creates small cognitive load

Severity: low.

Raised by: Claude.

Evidence:

- Feature wording naturally says `add blocker <blocker> to <target>`.
- Domain methods use `(target, blocker)`.
- Step definitions bridge the two by swapping arguments.

Concern:

This is mostly acceptable because feature language and domain API each use their natural order, but it can be a source of mistakes while reading/refactoring tests.

Decision: leave as-is.

Feature language and domain API each use their natural ordering: scenarios say “add blocker <blocker> to <target>”, while domain/application calls are target-first because they mutate the target yak. The bridge in step definitions is acceptable and no extra abstraction is needed now.

## Additional Decision: Show readiness reasons in tree/show

Matt wants readiness to be visible in human tree/show output before this parent closes. Create/implement child yak `show readiness reasons in tree and show`.

Important CQRS note: projections should not load/call the `YakMap` aggregate to derive readiness. Readiness remains derived from source facts, but tree/show/JSON/future projections need one canonical read-side readiness projection/view model so they do not each compute it differently. Do not add durable `YakBlocked` / `YakUnblocked` source events unless a future design deliberately treats readiness transitions as domain facts.
