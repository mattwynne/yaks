# Agent-Aware Help Examples

## Problem

`yx --help` shows the same examples regardless of who's reading them.
Humans and AI agents have different needs — humans want a getting-started
flow, agents want to see flags like `--format json` and stdin patterns
like heredocs.

## Decision

Show different examples in `yx --help` based on whether the session is
an agent session. This also changes the example style to use quoted
yak names (e.g. `"fix the flaky test"`) for clarity in both modes.

## Scope

This applies to top-level `yx --help` and `yx` (no args) only.
Subcommand help (e.g. `yx add --help`) is out of scope.

## Detection

Add `is_agent_session(&self) -> bool` to `LocalWorkspacePort`. The real
adapter checks `CLAUDECODE=1` (extensible to other agent env vars
later). Replace the existing `in_claude_code_session()` free function
in `main.rs` with this port method — both the plugin hint and the new
help examples use it.

## Help on DisplayPort

Help is a display concern. Add `show_help(&self, is_agent: bool)` to
`DisplayPort`. Each display adapter renders help appropriately:

- `TuiDisplay` / `ConsoleDisplay`: use clap's
  `Cli::command().after_help(examples).render_help()` internally,
  choosing examples based on `is_agent`
- `JsonDisplay`: could return structured help if needed in future

This keeps clap as an infrastructure detail inside the display adapter,
not something the use case or domain knows about. The example string
constants live in the display adapter alongside the clap rendering.

## Help as a Use Case

Route help through the normal command/use-case path. The use case
calls `workspace.is_agent_session()` and passes the result to
`display.show_help(is_agent)`.

Both the no-args path and the `--help`/`-h` path route to this use
case. To handle `--help` before clap intercepts it, detect the flag
early in `main.rs` and route to the use case instead of calling
`Cli::parse()`.

## Examples

### Human

```
yx add "fix the flaky test"
yx add "upgrade auth library" --under "fix the flaky test"
yx list
yx show "fix the flaky test"
yx start "fix the flaky test"
yx tag "fix the flaky test" bug
yx field "fix the flaky test" priority <<< "high"
yx list --tag bug
yx done "fix the flaky test"
```

### Agent

```
yx add "fix the flaky test" --under "parent yak"
yx show "fix the flaky test"
yx context "fix the flaky test" <<< $(cat <<'EOF'
The login test fails intermittently due to a race
condition in the session cleanup code.
EOF
)
yx field "fix the flaky test" plan <<< "Step 1: ..."
yx tag "fix the flaky test" bug
yx list --tag bug --format json
yx done "fix the flaky test"
```

## Testing

New `features/help.feature` with Cucumber scenarios using
`InProcessWorld`. The `TestWorkspace` adapter needs to become
configurable (e.g. via a field + constructor) to support returning
true/false for `is_agent_session()`.

- Scenario: human sees human examples (default)
- Scenario: agent sees agent examples (agent session enabled)

Assert on distinctive strings from each set (e.g. `--format json`
for agent, `yx start` for human).

## ADR

An ADR records this decision. Key alternatives considered:
- Static examples (status quo) — simple but unhelpful for agents
- Separate `yx help-agent` command — discoverability problem
- Dynamic after_help before parse — simple but keeps clap in main.rs
  rather than behind DisplayPort
- show_help on DisplayPort (chosen) — clap is an infrastructure
  detail inside the adapter, consistent with hexagonal architecture
