# Goal

Decide how to migrate existing yaks whose stored state is `blocked` if blocked becomes derived availability rather than workflow state.

# Questions

- Do existing blocked yaks become `todo` plus an unresolved external blocker?
- Do we need an explicit external/manual blocker concept?
- How should old event logs be interpreted?
- Can this be backward-compatible in projections?

# Acceptance / BDD Requirements

This yak should include feature-level Gherkin coverage for compatibility and migration behaviour. The migration behaviour should be documented in scenarios before or alongside implementation.

Suggested feature coverage:

- Existing yaks with stored `.state = blocked` are still readable after upgrading.
  - Given a repository/store created with the old blocked-state model
  - When I list or show the yak
  - Then the command succeeds and the yak is represented according to the new model.
- Existing blocked yaks have a clear migrated workflow state.
  - Decide and specify whether they become `todo`, `wip`, or something else.
  - Scenario should assert the chosen workflow state explicitly.
- Existing blocked yaks have clear availability semantics.
  - If they become manually/external blocked, assert they do not appear in `yx list --ready`.
  - If they simply become `todo`, assert they do appear when otherwise ready.
- Event log/history remains understandable.
  - Old `blocked` state events should not crash log/show/list.
  - If narrative changes, specify expected wording.
- Migration is idempotent/backward-compatible.
  - Running reset/migration twice does not create duplicate blockers or alter state repeatedly.
- Completion and state commands reflect the new model.
  - If `blocked` is removed as a valid state, scenarios should assert the new error/help text.
  - If legacy input is still accepted as sugar, scenarios should assert exactly what it does.

# Test Guidance

- Use Gherkin scenarios to capture user-facing compatibility promises.
- Use fixture-style steps for old-format stores/events where possible, similar to existing schema migration feature coverage.
- Keep lower-level unit tests for projection/event interpretation details.
- Be explicit about the difference between:
  - stored historical `blocked` state/events
  - new workflow state
  - derived readiness/availability
