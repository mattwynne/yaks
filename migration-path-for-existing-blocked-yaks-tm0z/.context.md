# Goal

Remove `blocked` as a stored workflow state and migrate existing blocked yaks to the new model: workflow state plus derived availability.

# Decision

`blocked` should no longer be a workflow state.

Workflow state should be only:

- `todo`
- `wip`
- `done`

Being blocked is derived availability/readiness, represented by blockers.

We need manual/external blockers for cases where a yak is blocked by a reason rather than by another yak.

# Manual / External Blockers

Support blocking a yak without another yak as the blocker.

Example:

```bash
yx blocker add deploy --reason "waiting for credentials"
```

This means `deploy` is still workflow-state `todo`, but it is not ready because it has a manual blocker.

Suggested view shape:

```json
{
  "name": "deploy",
  "state": "todo",
  "ready": false,
  "blocked_by": [
    {
      "kind": "manual",
      "reason": "waiting for credentials"
    }
  ]
}
```

Yak-to-yak blockers continue to work as today:

```bash
yx blocker add deploy --by "fix bug" --reason "needs fix first"
```

Suggested view shape:

```json
{
  "kind": "yak",
  "id": "fix-bug-1234",
  "name": "fix bug",
  "state": "todo",
  "reason": "needs fix first"
}
```

# CLI Semantics

## Add manual blocker

```bash
yx blocker add <yak> --reason <reason>
```

If `--by` is omitted, the blocker is manual/external.

A manual blocker should require a non-empty reason. `yx blocker add deploy` with neither `--by` nor `--reason` should fail clearly.

## Remove manual blocker

Pick a simple removal syntax during implementation, with Gherkin coverage. Preferred options:

```bash
yx blocker rm <yak> --manual
```

or, if multiple manual blockers are not supported:

```bash
yx blocker clear <yak>
```

Default recommendation: support one active manual blocker per yak for now to keep the model simple. Adding a new manual blocker reason updates/replaces the existing manual blocker reason rather than creating a list of indistinguishable manual blockers.

## State command

`blocked` is no longer an accepted target state:

```bash
yx state deploy blocked
```

should fail and explain that valid states are `todo`, `wip`, `done`, and that blocking is now done with `yx blocker add deploy --reason ...`.

# Migration Semantics

Existing historical yaks/events with stored state `blocked` must remain readable.

When projecting/replaying old `blocked` state:

- workflow state becomes `todo`
- a manual blocker is added
- default reason: `Migrated from blocked state`
- readiness is false
- list/show JSON reports `state: "todo"`, `ready: false`, and a manual blocker

Migration must be idempotent:

- replaying/resetting/migrating more than once must not duplicate manual blockers
- compaction after migration should store the new model, not reintroduce `.state = blocked`

Historical logs should remain understandable. Old events that set state to blocked should not crash log/show/list. Narrative can either preserve the historical wording or explain the migrated meaning, but must be covered by tests.

# Acceptance / BDD Requirements

Use feature-level Gherkin for user-visible compatibility and command behaviour.

Scenarios should cover:

## Manual blockers

- Add a manual blocker with a reason:
  - Given `deploy` is todo
  - When I run `yx blocker add deploy --reason "waiting for credentials"`
  - Then `deploy` has state `todo`
  - And `deploy` is not ready
  - And JSON shows a manual blocker with that reason
  - And `yx start deploy` fails because it is not ready

- Remove a manual blocker:
  - Given `deploy` has a manual blocker
  - When I remove/clear the manual blocker
  - Then `deploy` becomes ready if otherwise unblocked

- Adding a manual blocker without a reason fails clearly.

## Removing blocked workflow state

- `yx state deploy blocked` fails:
  - error mentions valid states: `todo`, `wip`, `done`
  - error suggests `yx blocker add deploy --reason ...`
  - no state event is emitted

- Help text for state commands no longer lists `blocked` as a valid workflow state.

## Migration / backward compatibility

- Existing old-format blocked yak remains readable:
  - Given a repository/store created with `.state = blocked`
  - When I list/show it
  - Then command succeeds
  - And the yak is represented as `state: todo`, `ready: false`
  - And JSON shows a manual blocker reason `Migrated from blocked state`

- Old blocked state events do not crash log/show/list.

- Migration/reset is idempotent:
  - Running reset or replay twice does not create duplicate manual blockers.

- Compaction after migration does not persist `blocked` as a workflow state.

# Implementation Notes

Keep manual blockers in the same conceptual blocker projection as explicit yak blockers, but distinguish them by kind/type.

Possible event designs:

- extend blocker events to allow `blocker_id: None` plus reason
- or add separate `ManualBlockerAdded/Updated/Removed` events

Choose the smallest clean design that keeps event parsing and projections understandable.

Manual blockers are not graph edges and therefore do not participate in blocker cycle detection. They only affect readiness/completion/start guards.

Completion semantics:

- A yak with an active manual blocker should not be startable.
- A yak with an active manual blocker should not be markable done by default, mirroring explicit yak blockers.
- Removing/clearing the manual blocker should be required first unless a future deliberate override is designed.

# Out of Scope

- Multiple named/manual blockers per yak, unless implementation turns out simpler than replacement semantics.
- Rich external blocker metadata beyond a reason string.
- New override/blast-through flags.
- Changing hierarchy blocker semantics.
