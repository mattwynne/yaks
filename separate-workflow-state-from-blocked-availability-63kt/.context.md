# Goal

Separate a yak's intrinsic workflow state from whether it is currently blocked/available.

# Problem

We currently model `blocked` as one of the workflow states alongside `todo`, `wip`, and `done`. That is starting to feel wrong:

- a yak can be blocked by other yak(s) regardless of its workflow state
- parent yaks with incomplete children are not really `wip`; they are unavailable until their children are done
- once all child yaks are done, the parent should look ready/actionable again
- explicit sibling dependencies and parent/child decomposition seem to be the same design space

# Design Direction

Consider modelling:

- workflow state: `todo | wip | done`
- availability/readiness: derived from blockers such as incomplete children or explicit `blocked_by` relationships

A yak is ready when it is not done, not otherwise unavailable, and all blockers are resolved.

# Suggested Order

1. `model parent readiness from child completion` — solve the concrete parent/child readiness problem first.
2. `update list ready and wip semantics` — make the new readiness semantics visible and useful.
3. `replace blocked state with blocked_by relationship` — generalise parent/child blocking into explicit dependency relationships.
4. `migration path for existing blocked yaks` — once the target model is clearer, decide how existing `blocked` states should be interpreted.

# Open Questions

- Should `blocked` remain a stored state, or become derived presentation?
- Are child yaks literally blockers, or just interpreted as blockers by readiness logic?
- Can a `wip` yak be blocked, and how should that be shown?
- What is the migration path for existing `blocked` yaks?
- How does this interact with fuzzy state-changing commands and existing status help?
