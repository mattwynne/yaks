# Goal

Separate a yak's intrinsic workflow state from whether it is currently blocked/available.

# Status

Done. Implementation, migration, acceptance coverage, architectural cleanup, and docs review are complete.

# Problem

We previously modelled `blocked` as one of the workflow states alongside `todo`, `wip`, and `done`. That was wrong because:

- a yak can be blocked by other yak(s) regardless of its workflow state
- parent yaks with incomplete children are unavailable until their children are done
- once all child yaks are done, the parent should look ready/actionable again
- explicit sibling dependencies and parent/child decomposition live in the same design space

# Current Model

- workflow state: `todo | wip | done`
- readiness/availability: derived from blockers such as incomplete children, explicit yak blockers, manual/external blockers, and workflow state

A yak is ready when it is `todo` and all blockers are resolved. `wip` and `done` yaks can still have blockers shown, but they are not ready because ready means actionable/startable next.

# Completed Slices

- parent readiness from child completion / list-ready semantics
- explicit blocker relationships via `yx blocker add <yak> --by <blocker>`
- guard starting non-ready yaks
- blocker graph edge cases: idempotence, circular dependency validation, completion guards, cleanup, move validation
- manual blockers via `yx blocker add <yak> --reason ...`
- migration/backwards compatibility for legacy stored/evented `blocked` state
- acceptance coverage for legacy migration/replay/compaction/manual blocker guards
- whole-aggregate compaction snapshot preserving yaks, removed IDs, yak blockers, and manual blockers
- unified blocker domain model/events with `BlockerSource::Yak` and `BlockerSource::Manual`
- human readiness reasons in `yx show` and tree/list output, derived from read-side facts
- vivid blocker feature examples
- architecture and user docs review/update

# Final Review Outcome

`architectural and docs review sweep` is complete. Docs and yak contexts now consistently describe:

- workflow state vs derived readiness/availability
- `yx list --ready`
- JSON `ready`, `blocked_by`, and readiness-detail output for agent/script consumption
- `yx list --only not-done` remaining workflow-state based
- parent/child readiness and incomplete-child blockers
- explicit yak blocker and manual blocker semantics
- migration/compatibility behaviour for legacy `blocked` state/events

# Decisions

- `blocked` is no longer a stored workflow state.
- Child/descendant incompletion is an implicit readiness blocker, not an explicit `BlockerAdded` event.
- WIP yaks can have blockers shown via `blocked_by`, but WIP yaks are not `ready` because `ready` means actionable/startable next.
- Existing legacy `blocked` state/events are projected as `todo` plus a manual blocker reasoned `Migrated from blocked state`.
- User-facing cycle errors now say `circular dependency` rather than `blocker cycle`.
- Blocker path modelling uses a named `BlockerPath` type; hierarchy-kind is not exposed because it is not currently needed in user-facing errors.
