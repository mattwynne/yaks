## Problem

The JSON output from `yx show --format json` is missing information that
tooling needs, and the ancestor data is pre-formatted for display rather than
structured.

### Missing IDs on children

`YakChildView` carries only `name` and `state` — no `id`. Tooling (e.g. the
`show_yak` pi extension) can't programmatically refer to a child yak after
reading it from the show output.

Note: the shown yak's own `id` was added recently and is already present in
`YakDetailView`.

### Presentation-leaky breadcrumbs

`YakDetailView` has `breadcrumb: Vec<String>` — a flat list of ancestor names,
pre-formatted for display. The view model should provide structured data; the
display adapter should decide how to format it.

Ancestors should carry id, name, and state — so any consumer can work with
them uniformly.

## What changed recently

**ADR 0018 (Unify Yak types):** `YakView`, `YakEntry`, and `YakSnapshot` were
consolidated into a single `Yak` struct. There's now one domain type with all
fields (id, name, parent_id, state, context, fields, tags, created_by,
created_at).

**ADR 0019 (Event-source the aggregate):** The `YakMap` aggregate now loads by
replaying events via `from_events()`. The read model (`.yaks/` directory) is
purely a query-side projection.

**View types moved to adapter layer:** `YakDetailView`, `YakChildView`,
`YakTreeNode`, etc. now live in `src/adapters/views.rs`, not in the domain.
This is the right place for presentation-oriented structs.

## Design approach

Since the view types are already in the adapter layer, the simplest approach is
to enrich the existing structs:

1. **Add `id` to `YakChildView`** — straightforward, the data is already
   available from the `Yak` struct when building the view.

2. **Replace `breadcrumb: Vec<String>` with structured ancestors** — use a
   `Vec<YakAncestorView>` (or reuse `YakChildView` with the added `id`) to
   carry `{id, name, state}` per ancestor. The pretty display adapter formats
   this as "grandparent > parent >" as before; the JSON serializer emits the
   full structured data.

There's no need for a new domain type — the `Yak` struct already has
everything. The view structs are lightweight projections for display/JSON.

## Scope

1. Add `id` to `YakChildView`
2. Replace `breadcrumb: Vec<String>` with `Vec<YakAncestorView>` carrying id,
   name, and state (or reuse `YakChildView` if the shape is identical)
3. Update `show_yak.rs` use case to populate the new fields from `Yak` data
4. Update display adapters (pretty + JSON) to format from structured data
5. Update Rust tests and the show-yak pi extension test
