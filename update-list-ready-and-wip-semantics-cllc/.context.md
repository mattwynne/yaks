# Goal

Update user-facing status/readiness semantics after separating workflow state from availability.

# Why This Exists

The first slice, `model parent readiness from child completion`, may add/clarify a domain readiness rule without fully exposing it in the UI. We need to circle back here so users and agents can actually see which yaks are ready/actionable.

# Areas To Review

- `yx list` rendering
- any ready/actionable yak logic
- `yx start`, `yx done`, and `yx state`
- help text for states/status
- JSON output fields: distinguish workflow state from derived availability
- possible filters or commands for ready yaks, e.g. `yx list --ready` or future `yx prime`

# Desired Outcome

Users can tell the difference between what workflow state a yak is in and whether it is currently actionable.

# Open Questions

- Should ready be a JSON boolean field, a rendered marker, a filter, or all of these?
- How should a todo parent with incomplete children render?
- How should a wip yak with blockers render once explicit blockers exist?
- Should `yx list --only not-done` include unavailable parents, or should there be a separate actionable/ready view?
