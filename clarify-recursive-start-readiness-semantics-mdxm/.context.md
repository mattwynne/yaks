# Context

Follow-up from `guard starting non ready yaks`.

We preserved existing `yx start --recursive` bulk behavior while adding the non-recursive readiness guard. This yak records the explicit design decision for that behavior; it does not change application code.

## Decision

- Non-recursive `yx start <yak>` is the actionable command for beginning work on a single yak. It requires the target yak to be ready before changing it to `wip`.
- `yx start --recursive <yak>` remains an explicit bulk workflow-state operation. It is equivalent in spirit to recursively setting workflow state to `wip` for the root and descendants.
- Because recursive start is a bulk state operation, it intentionally bypasses the readiness guard for both the root yak and all descendants.
- Recursive start does not remove or resolve explicit blockers, and it does not alter the yak hierarchy. It only changes stored workflow state.
- Recursive start is allowed to mark a parent with incomplete children and descendants as `wip`. This preserves existing behavior and is now covered by the regression scenario added in the previous yak.
- Any future redesign, deprecation, or rename of recursive start can happen later, but is out of scope for this slice.

## Acceptance notes

- The readiness guard applies to `yx start <yak>` without `--recursive`.
- The readiness guard does not apply to `yx start --recursive <yak>`.
- Explicit blockers are preserved across recursive start; they are not cleared, resolved, or rewritten.
- Parent/child relationships are preserved across recursive start; no descendants are moved, deleted, or otherwise reorganized.
- Existing recursive-start behavior is intentionally documented rather than changed in this slice.

## BDD examples

### Non-recursive start requires readiness

Given a yak is not ready because it has incomplete children or explicit blockers
When I run `yx start <yak>`
Then the command is rejected by the readiness guard
And the yak state is not changed to `wip`.

### Recursive start bypasses readiness for the root

Given a parent yak is not ready because it has incomplete children
When I run `yx start --recursive <parent>`
Then the parent is marked `wip`
And its descendants are marked `wip`
And the hierarchy is unchanged.

### Recursive start bypasses readiness for descendants

Given a descendant yak is not ready because it has its own incomplete children or blockers
When I run `yx start --recursive <ancestor>`
Then that descendant is still marked `wip`
And its blockers and child relationships are preserved.

### Recursive start preserves explicit blockers

Given yak A is explicitly blocked by yak B
When I run `yx start --recursive <ancestor containing A>`
Then yak A may be marked `wip`
But yak A is still blocked by yak B
And no blocker relationship is removed or resolved.

## Non-goals

- Do not change application code in this slice.
- Do not change recursive-start semantics in this slice.
- Do not rename, deprecate, or remove `yx start --recursive` in this slice.
- Do not make recursive start resolve blockers or change hierarchy.
