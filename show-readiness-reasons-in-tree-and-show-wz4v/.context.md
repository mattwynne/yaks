# Goal

Make readiness visible and understandable in tree/list and show output before closing `separate workflow state from blocked availability`.

# Background

We separated workflow state (`todo | wip | done`) from derived readiness/availability. Right now readiness exists in JSON/list filtering and command guards, but the human tree/show views do not clearly explain why a yak is or is not ready.

Matt also raised a CQRS/projection concern: projections should not each independently derive readiness differently, and projections should not load aggregates to ask questions. We need a read-side representation/projection of readiness that tree/show can use consistently.

# Design Direction

Do not add durable source-of-truth `YakBlocked` / `YakUnblocked` events just to summarize derived state. Blocking/readiness remains derived from source facts:

- workflow state
- explicit yak blockers
- manual blockers
- incomplete children / hierarchy
- moves/removals/done/prune events

Instead, introduce or clarify a read-side readiness projection/view model that can consistently answer:

```rust
ReadinessView {
    ready: bool,
    reasons: Vec<ReadinessReason>,
}
```

Possible reasons:

- `state is wip`
- `state is done`
- `blocked by <yak>`
- `blocked by manual reason <reason>`
- `has incomplete children: <child paths>`

Exact shape and wording should be designed during implementation.

# User-Facing Behaviour

Add human-facing output that helps users understand readiness:

## Tree/list view

- The tree should make readiness/blocked-ness visible without reintroducing `blocked` as a workflow state.
- Incomplete children / explicit blockers / manual blockers should be understandable from the tree or an associated detail line.
- Avoid noisy output for normal ready yaks.

## Show view

`yx show <yak>` should include readiness details:

- whether the yak is ready
- if not, why not
- explicit yak blockers and manual blockers
- incomplete children if relevant
- state-based reasons (`wip`, `done`) where useful

JSON should remain machine-friendly and should expose the same conceptual information if it does not already.

# CQRS / Projection Constraint

Read-side code should not load/call `YakMap` aggregate just to answer readiness queries.

If current list/show does that, this yak should either:

- introduce a proper read-side readiness projection/reducer, or
- create a focused follow-up yak if the full projection refactor is too large

The goal is one canonical read-side derivation of readiness so tree/show/JSON/future TUI/watch commands do not drift.

# Acceptance Coverage

Use feature-level Gherkin for user-visible output.

Scenarios should cover tree/show readiness reasons for:

- ready todo leaf yak
- todo parent with incomplete children
- yak blocked by another yak
- yak with a manual blocker
- wip yak not ready because it is already in progress
- done yak not ready because it is done

Prefer vivid examples such as `deploy release`, `security review`, `publish announcement`, and `waiting for credentials`.

# Definition of Done

- Human tree/list and show output make readiness understandable.
- The model does not reintroduce `blocked` as a stored workflow state.
- Readiness derivation for read models is centralized or a concrete follow-up yak is created for any remaining projection refactor.
- Feature tests document the new output semantics.
- Relevant checks pass.
