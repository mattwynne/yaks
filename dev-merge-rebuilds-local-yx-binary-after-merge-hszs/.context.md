# Problem

After `dev merge <branch>`, the source on `main` is fast-forwarded, but the local `yx` binary may still be stale.

This matters because we dogfood `yx` while developing it. For example, after merging the change for canonical event payloads, `yx events wait-for-next` still emitted the old payload shape because the CLI binary being executed had not been rebuilt from `main`.

# Decision

Update `bin/dev merge` so that, after a successful fast-forward merge to `main`, it rebuilds the release binary from `main`.

No install/copy step is needed: the local setup is expected to use the rebuilt binary via symlink/path to `target/release/yx`.

# Acceptance Criteria

- `dev merge <branch>` still performs its existing flow: require main, rebase/check branch, fast-forward main, remove worktree, delete branch, mark yak done.
- After the fast-forward merge succeeds, `dev merge` runs `cargo build --release --quiet` from `main`.
- If the post-merge rebuild fails, `dev merge` reports a clear warning/error explaining that the merge succeeded but the local binary may be stale.
- The rebuild is post-merge only; merge checks in the branch worktree remain unchanged.
