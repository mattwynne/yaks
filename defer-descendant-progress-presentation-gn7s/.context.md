# Goal

Record the presentation concern separately from the blocker state model.

# Decision / Framing

Stored workflow state means direct work on this yak, not roll-up progress from descendants.

A parent can have work in progress underneath it without its own stored state becoming `wip`.

Example:

```text
- [todo] deploy
  - [wip] fix bug
```

This means:

- direct work on `deploy` has not started
- work under `deploy` is in progress
- `deploy` is not ready while `fix bug` is incomplete
- once children are done, `deploy` can become ready again because its own direct state is still `todo`

# Minimal Acceptance Coverage

Include a small scenario using existing tree/markdown output so this behaviour is visible and documented without adding new UI yet:

```gherkin
Scenario: A parent shows work in progress underneath without becoming wip
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug" under "deploy"
  When I start "fix bug"
  And I list the yaks in "markdown" format
  Then the output should be:
    """
    - [todo] deploy
      - [wip] fix bug
    """
```

# Out of Scope for First Blocker Slice

Do not add richer descendant progress presentation in the first blocker implementation unless it becomes necessary.

Possible later improvements:

- derived `has_wip_descendant` in JSON
- progress counts, e.g. `2/5 children done`
- human UI hints such as “in progress underneath”
- sorting/grouping based on descendant progress

Keep this separate from the core event/state model to avoid mixing presentation with stored workflow state.
