# Goal

Show when a parent has work in progress underneath it, without changing the parent’s stored workflow state.

# Decision / Framing

Stored workflow state means direct work on this yak, not roll-up progress from descendants.

A parent can have work in progress underneath it without its own stored state becoming `wip`.

Example data model:

```text
- [todo] deploy
  - [wip] fix bug
```

This means:

- direct work on `deploy` has not started
- work under `deploy` is in progress
- `deploy` is not ready while `fix bug` is incomplete
- once children are done, `deploy` can become ready again because its own direct state is still `todo`

# In Scope: Muted Green Filled Indicator

In the human pretty/tree UI, a todo yak with a wip descendant should get a subtle “in progress underneath” presentation: a **muted green filled state indicator**.

This must be weaker than the existing/current wip indicator, but still visibly green. Use regular filled indicator glyph `●` with darker muted 256-colour green 64.

Use ANSI styling for indicators only:

- normal todo: default/plain open indicator, e.g. `○ deploy`
- wip yak itself: current active wip indicator, but do not color the yak name/text
- todo yak with a wip descendant: muted green filled indicator only, e.g. ANSI `\x1b[38;5;64m●\x1b[0m deploy`
- the yak name/text should stay the normal/default text color
- done yak: current done/dim style, not muted green

Example pretty output conceptually:

```text
\x1b[38;5;64m●\x1b[0m deploy
  \x1b[32;1m●\x1b[0m fix bug
```

Rendered intent:

```text
● deploy       # only the regular filled indicator is dark muted green: todo, but work is happening underneath
  ● fix bug    # only the indicator has normal active wip styling; text is default
```

This is presentation-only:

- do not mutate the parent’s `.state`
- do not emit a parent state event
- markdown/plain output should continue to show the stored state (`todo`)
- JSON should continue to report the stored state as `todo`

# Acceptance Coverage

Include a scenario using markdown output to lock the state-model behaviour:

```gherkin
Scenario: A parent shows work in progress underneath without becoming wip
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug" under "deploy"
  When I start "fix bug"
  And I list the yaks in "markdown" format
  Then the output should be:
    """
    - [todo] deploy
      - [wip] fix bug
    """
```

Include focused coverage for the pretty/tree muted green presentation:

- a todo parent with a wip descendant has a muted-green filled state indicator/glyph
- assert ANSI styling when color is enabled; the parent indicator should use muted green (`\x1b[38;5;64m` or equivalent existing style abstraction)
- the parent yak name/text should not be colored green
- a todo parent with no wip descendant is not styled that way
- a wip yak itself keeps the normal active wip indicator styling, without coloring the yak name/text
- a done parent is not shown as in-progress-underneath just because of stale/odd descendants

# Out of Scope

Do not add broader progress features in this slice unless needed for the muted green styling:

- progress counts, e.g. `2/5 children done`
- sorting/grouping based on descendant progress
- changing readiness semantics
- changing stored parent state semantics

Keep this separate from the core event/state model to avoid mixing presentation with stored workflow state.
