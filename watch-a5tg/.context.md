# Goal

Add an `yx events` command group with event-streaming commands for watching a yak subtree:

- `yx events watch <yak> [--timeout <duration>]`
- `yx events wait-for-next <yak> <event-type> [--timeout <duration>]`

Both commands emit matching domain events as NDJSON so agents/scripts can supervise or wait on work in another part of the yak tree.

# Type

Feature

# Success Criteria

- `yx events watch <yak>` resolves the yak by the same fuzzy matching rules as other yak-name commands.
- `yx events watch <yak>` streams events affecting the selected yak or any current descendant.
- Subtree membership is dynamic: moves into/out of the watched subtree change what is watched, while the boundary move/removal event itself is emitted when it affects the watched subtree.
- Output is NDJSON only: one JSON object per line, no human-readable mode.
- `yx events watch <yak>` keeps running until interrupted, stdout closes, or `--timeout` expires.
- `yx events watch <yak> --timeout <duration>` exits `0` after the duration, after streaming any matching events during that window.
- `yx events wait-for-next <yak> <event-type>` waits for the next matching event type in the watched subtree, emits it, then exits `0`.
- `yx events wait-for-next <yak> <event-type> --timeout <duration>` exits non-zero on timeout, prints the timeout error to stderr, and keeps stdout pure domain-event NDJSON.
- Both commands flush each line promptly so another process/agent can consume it.
- Both commands report clear errors for unknown/ambiguous yak names and unsupported event types.

# Architecture Decisions

- Rename/clarify the existing in-process event fanout as a local event bus / event dispatcher. It is for events produced inside one `yx` process and used to update projections.
- Add a `GlobalEventBus` abstraction for subscribing to the durable event stream across processes.
- `GlobalEventBus` is an application/infrastructure port, not a domain concern. The domain emits facts; infrastructure decides how processes observe committed facts.
- The first implementation should be git-backed:
  - internally watch git event-store refs/files with a filesystem watcher (`notify` crate), e.g. `.git/refs/notes/yaks`, `.git/packed-refs`, and relevant parent dirs for lock/rename updates
  - keep an event-store cursor from subscription start
  - reread events via `EventStoreReader` when the filesystem says the event store may have changed
  - fall back to polling if filesystem watching is unavailable or unreliable
- The `GlobalEventBus` should expose committed `YakEvent` batches or equivalent subscription API; callers should not know about git refs or filesystem notifications.
- This abstraction should also support future live features, especially a live TUI, and leaves room for future daemon/P2P/Automerge-backed event subscriptions without changing `yx events` callers.

# Design Decisions

- Use an `events` command group instead of a top-level `watch` command:
  - `watch` is for indefinite/bounded streaming.
  - `wait-for-next` is for one matching event then exit.
- Scope is subtree-based: selected yak plus descendants.
- Initial output should not dump historical events; watching starts from “now”.
- Waiting for computed/projected state (e.g. yak becomes ready/done) is out of scope for v1 and can be added later as a separate command.
- NDJSON objects should include enough stable data for agents:
  - event id
  - event type
  - affected yak id
  - affected yak name if resolvable
  - timestamp
  - author
  - narrative / useful event data
- No pretty/human format in v1.

# Open Modelling Questions

## Event identity / cursor

What should `GlobalEventBus` use as its cursor?

Options:
- event IDs
- git commit SHAs / ref tip
- stream position / event count

Recommendation so far: event IDs are useful for delivered event identity, but the git adapter probably needs an internal git-tip/commit-based cursor to robustly detect events after subscription.

## Compaction while watching

If `yx compact` happens during a subtree watch, should the watcher:

- emit a `Compacted` notification,
- ignore it,
- reset/rebase its cursor silently,
- or warn on stderr?

Compaction is stream-level rather than yak-specific, so it is unclear whether it belongs in `yx events watch <yak>` output.

## Reset / history rewrite while watching

If the event ref is rewritten by reset/sync/compaction and the watcher’s cursor can no longer be found, how should it behave?

Recommendation so far: detect the lost cursor, resubscribe from the current tip without historical replay, and possibly warn on stderr. Stdout should remain pure event NDJSON.

## Event type names

What exact event type names should `yx events wait-for-next <yak> <event-type>` accept?

Options:
- Rust enum variant names, e.g. `BlockerRemoved`
- kebab-case CLI names, e.g. `blocker-removed`
- both, with one canonical output form

Recommendation so far: canonical output can use Rust/domain variant names, while CLI input may accept ergonomic aliases.

## Subtree filtering for relationship events

For events that reference multiple yaks, especially blocker events, when is the event relevant to a watched subtree?

Options:
- emit only when the primary affected yak / target is in the watched subtree
- emit when any directly referenced yak is in the watched subtree

Recommendation so far: emit when any directly referenced yak is in the watched subtree. Otherwise a watched yak could block/unblock something elsewhere and the watcher would miss that its watched yak was involved.

## Root/global event watch

Should v1 include `yx events watch --all` or another way to watch the entire event stream?

Not required for the current subtree-watch goal, but `GlobalEventBus` should not assume all consumers will always have a subtree filter. A future live TUI may want all events.

## NDJSON envelope shape

Should the event notification include structured raw event data as well as narrative text?

Recommendation so far: yes. Include top-level convenience fields (`event_id`, `event_type`, `yak_id`, `yak_name`, `timestamp`, `author`, `narrative`) plus a structured `event` object with event-specific fields.

## Read model freshness / subtree projection

When a watcher process receives an event created by another process, should it rely on the disk `.yaks` projection already being updated by that other process, or maintain its own in-memory projection from events?

Trade-off:
- Rereading `.yaks` is simpler but may race with projection updates and makes dynamic move/remove boundary behaviour more subtle.
- An in-memory projection inside the watcher is cleaner for correctness and future live TUI use, but larger in scope.

Recommendation so far: decide explicitly before coding the watcher. This is likely the most important design question for dynamic subtree correctness.

# Example Map

Feature: event watching

  Rule: Target resolution
    Example: Given a yak `deploy`, `yx events watch deploy` starts watching `deploy`.
    Example: Given yaks `deploy app` and `deploy docs`, `yx events watch deploy` fails as ambiguous and exits.
    Example: Given no matching yak, `yx events watch deploy` fails with the normal not-found style error and exits.
    Example: Given `project` with child `fix bug`, `yx events watch "fix bug"` can target the child directly.

  Rule: Subtree filtering is dynamic
    Example: Given `project` with child `fix bug`, when watching `project` and `fix bug` changes state, one NDJSON event is emitted.
    Example: Given `project` and unrelated `admin`, when watching `project` and `admin` changes, no event is emitted.
    Example: Given `project` with child `fix bug`, when watching `fix bug` and `project` changes, no event is emitted because ancestors are outside the watched subtree.
    Example: Given `project` with nested descendant `frontend/login`, when watching `project` and `login` changes, one NDJSON event is emitted.
    Example: Moving a yak into the watched subtree surfaces the move event, and future events for that yak are watched.
    Example: Moving a yak out of the watched subtree surfaces the move event, then future events for that yak are ignored.
    Example: Removing a watched descendant surfaces the removal event, then future events for that removed yak are irrelevant/ignored.

  Rule: Watching starts from now
    Example: Given `project` already exists, when I run `yx events watch project`, no historical `Added project` event is emitted.
    Example: Given `project` exists, when I start `yx events watch project` and then run `yx done project`, the done event is emitted.
    Example: Given `project` has historical child changes, when I start watching `project`, those historical child changes are not emitted.

  Rule: Events are emitted as NDJSON
    Example: When a watched yak is started, stdout gets one line of valid JSON ending with a newline.
    Example: When two relevant changes happen, stdout gets two JSON lines in event order.
    Example: Each object includes at least `event_id`, `event_type`, `yak_id`, `yak_name`, `timestamp`, `author`, and `narrative`.
    Example: Output contains no pretty text, spinner, colours, or prompts.

  Rule: Command mode controls when the process exits
    Example: `yx events watch project` streams matching events indefinitely until interrupted.
    Example: `yx events watch project --timeout 30s` streams matching events for 30 seconds, then exits `0`.
    Example: `yx events wait-for-next project BlockerRemoved` emits the next matching `BlockerRemoved` event in the watched subtree, then exits `0`.
    Example: `yx events wait-for-next project BlockerRemoved --timeout 30s` exits non-zero if no matching event arrives within 30 seconds.
    Example: On wait-for-next timeout, stdout is empty and stderr says it timed out waiting for `BlockerRemoved`.

  # Deferred:
  # - Waiting for computed/projected state, e.g. `wait-until done` or `wait-until ready`.
  # - Historical replay/tail options such as `--since`.
