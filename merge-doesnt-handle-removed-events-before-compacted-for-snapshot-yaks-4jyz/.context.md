# Problem

After syncing a stale repo (yaks2, schema v5) with a current remote (schema v7), zombie yaks reappeared — yaks that had been done and removed on the remote were back in the list as if they'd never been touched.

# Root Cause (confirmed via exploratory testing)

In `src/adapters/event_store/mod.rs:53-127`, the `merge_event_streams()` function has "orphan" logic:

1. After merging and sorting events from both peers, it finds the `Compacted` event
2. It collects all events **before** Compacted that affect yaks **not in the snapshot** — these are called "orphans"
3. It **moves orphans after** the Compacted event, assuming they're "missed" events that should be preserved

**The bug:** When Alice removes beta and compacts (snapshot = `[alpha, gamma]`), and Bob's stale `Added beta` arrives, the merge sees it affects a yak not in the snapshot, classifies it as an orphan, and moves it after Compacted. On replay: Compacted creates `[alpha, gamma]`, then `Added beta` recreates the zombie.

**The fundamental design gap:** The `Compacted` event only stores current state (`Vec<Yak>`) — it has no record of which yaks were removed. So the merge can't distinguish between "yak was removed before compaction" and "yak was created on another peer after compaction".

## Reproduction

100% reproducible with this scenario:

```
T1  Alice: Added alpha, beta, gamma
T2  Bob:   Added alpha, beta, gamma
T3  Alice: Done beta → Removed beta
T4  Alice: Compact → snapshot [alpha, gamma]
T5  Bob:   Sync with Alice → beta reappears as zombie
```

After sync, Bob has 3 yaks instead of 2. The event log shows Bob's `Added beta` placed after Alice's `Compacted` event.

## Key Code References

- **Merge logic (the bug):** `src/adapters/event_store/mod.rs` — `merge_event_streams()` lines 53-127, orphan detection at lines 81-97
- **Sync protocol:** `src/adapters/event_store/sync.rs` — `sync_with_remote()` lines 38-154
- **Compaction:** `src/application/compact_events.rs` — `CompactEvents::execute()` lines 24-60

The same event ID `019ca7a8-11f0-7bd3-b307-237d75dd296b` had different content in the two repos:

**Main repo:**

Same event ID, different SHA, completely different event type and content.

## Different compaction baselines

**Main repo (bottom of log):**
```
event: 019ca7a8-11f0-7bd3-b307-237d75dd296b  sha: 92f228b — tagged sync
event: 019ca7a5-96fe-76a2-a2c2-47d90522dc3f  sha: 36af4a9 — tagged sync

```

**yaks2 (bottom of log):**
```
event: 019ca7a8-11f0-7bd3-b307-237d75dd296b  sha: b38c827 — compacted (42 yaks)
event: migration-to-v7  sha: 79db908
```

yaks2 had a 42-yak compaction where main had a 31-yak compaction. The 42-yak version contained stale state including all the zombie yaks.

## Missing events

yaks2 had 519 events vs main's 594 — 75 events missing. Two events present in main were completely absent from yaks2:
- `019ca7a5-88c3` — the correct 31-yak compaction
- `019ca7a5-96fe` — a "tagged sync" event

Both sat between `migration-to-v7` and the event whose ID was reused (`019ca7a8-11f0`).

## Different migration-to-v7 SHAs

The `migration-to-v7` event had different git SHAs: `568e946` in main vs `79db908` in yaks2. This means the two repos independently created different migration compaction commits with the same event-id but different tree content.

# Sequence of events (original incident)

1. yaks2 was on schema v5 with old local state (42 yaks, from before many were done/removed on the remote)
2. User tried `yx sync` with the old v5 binary — got error because remote was at v7
3. User pulled main and rebuilt yx (now v7-capable)
4. User ran `yx sync` — migration v5→v7 ran on the local ref first (in `main()`), then sync ran
5. After sync, yaks2 showed zombie yaks and a corrupted event history
