# Goal

Revisit the Disco ↔ Yaks status mapping now that Yaks no longer has `blocked`/`stuck` as a workflow state.

# Background

Older Disco integration notes proposed adding `stuck` to Yaks as the equivalent of Disco `blocked`. That conflicts with the completed `separate workflow state from blocked availability` work:

- workflow state is `todo | wip | done`
- blocking/readiness is derived from hierarchy, explicit yak blockers, and manual blockers

# Questions

- Should Disco `blocked` map to a Yaks manual blocker?
- Should it map to derived readiness/presentation only at the Disco boundary?
- Should Yaks expose enough blocker/readiness data in WASM for Disco to present `blocked` without changing workflow state?
- How should Disco's upward status propagation map to Yaks' derived parent readiness/progress?
- Does this need an ADR before implementation?

# Definition of Done

- Updated integration plan/status mapping is documented.
- Child yaks for WASM bindings, Forest adapter, and status propagation are updated if needed.
- No new Yaks workflow state is introduced unless a deliberate superseding design decision is made.
