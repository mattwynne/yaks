# Disco Integration — needs status-model review

Yaks' domain model runs in the browser via WASM. Disco is the UI shell. CLI and browser share the same git data with CRDT merge for concurrent editing.

## Status Update after blocked-state removal

The previous plan said to add a new Yaks workflow state `stuck` to map Disco `blocked`.

That assumption is now stale. Yaks workflow state is intentionally only:

- `todo`
- `wip`
- `done`

Blocking/readiness is represented separately via explicit/manual blockers and derived readiness. Before implementing Disco status mapping, revisit the mapping decision. Likely options:

- map Disco `blocked` to a manual blocker / derived readiness rather than a workflow state,
- keep Disco-only blocked presentation at the integration boundary,
- or deliberately introduce a separate integration-specific concept with a new ADR/design decision.

Do **not** add `stuck` as a workflow state without a fresh design decision that accounts for `separate workflow state from blocked availability`.

## Decisions Made (2026-04-13, partly stale)

- CLI ↔ browser interop: yes, required for v1
- Concurrent multi-user editing: yes, via CRDT event merge
- Real-time sync: pull-based ok for now
- Architecture: Option B — full WASM domain
- Status mapping needs review because Yaks no longer uses blocked/stuck as workflow state.
