# Goal

Implement ADR 0024: replace timestamp-based `.last-checked` verification with a content-addressed, machine-readable local check record that `bin/dev check`, `.githooks/verify-checks`, and `bin/dev merge` can trust safely.

# Background

See `docs/adr/0024-content-addressed-check-verification.md`.

Current problem: `bin/dev check` writes an ignored timestamp marker. Hooks and `dev merge` can skip expensive checks based on mutable mtimes rather than the exact content and policy that passed.

# Desired Behaviour

A successful full `bin/dev check` writes `.last-checked.json` with a schema-versioned fingerprint of the verified workspace. Verification reuse is allowed only when the current workspace exactly matches the recorded fingerprint and the relevant tracked workspace/index state is clean.

`bin/dev check --force` ignores any existing record, reruns the suite, and overwrites the record on success.

`bin/dev merge` may reuse the record only after rebasing onto current `main`, so the fingerprint represents the candidate commit that would be fast-forwarded.

# Proposed Record v1

JSON, ignored locally, e.g. `.last-checked.json`:

- `schema_version: 1`
- `head`: `git rev-parse HEAD`
- `tree`: `git rev-parse HEAD^{tree}`
- `merge_base_main`: `git merge-base main HEAD` when `main` exists, otherwise null/absent by deliberate policy
- `checked_at`: informational timestamp only; never proof
- `check_version`: explicit policy version string, bumped whenever the check policy changes in a way not captured by file hashes
- `dev_script_blob`: `git hash-object bin/dev`
- `verify_script_blob`: `git hash-object .githooks/verify-checks`
- `fingerprints` for relevant config/lock inputs initially:
  - `Cargo.lock`
  - `Cargo.toml`
  - `.cargo/config.toml` if present
  - `.pre-commit-config.yaml` if present
  - `.shellspec`

Open policy decision before implementation: whether missing optional files are represented as `null`, omitted, or a `{present:false}` shape. Prefer explicit representation so mismatch messages are clear.

# Implementation Plan

## 1. Characterise existing behaviour

- Read `bin/dev`, `.githooks/verify-checks`, `dev merge`, and current ShellSpec coverage.
- Identify all current `.last-checked` reads/writes and any `.gitignore` entries.
- Keep this as a refactor of the development scripts, not domain code.

## 2. Add failing ShellSpec coverage first

Add focused tests for the user-visible contract from ADR 0024:

- reuse when all fingerprints match,
- rejection when `HEAD` changes,
- rejection when `Cargo.lock` changes,
- rejection when `bin/dev` changes,
- rejection for dirty tracked files,
- rejection for staged tracked files,
- `dev check --force` reruns and rewrites the record,
- `dev merge` reuses only after the branch has been rebased onto current `main`.

Prefer checking concise output reasons such as `checks already verified for HEAD ...` or `check record rejected: Cargo.lock changed`.

## 3. Extract script helpers

Implement small shell helpers, likely in `bin/dev` and/or a shared `bin/check-record` helper if duplication emerges:

- compute current fingerprint JSON,
- write record atomically after successful full check,
- compare current fingerprint with record,
- print the first/most useful mismatch reason,
- detect relevant dirty/staged tracked files without mtimes.

Keep JSON generation/parsing robust. Prefer `jq` if the repo already assumes it; otherwise use a small Python snippet to avoid adding a new dev dependency silently.

## 4. Replace timestamp logic

- Stop writing `.last-checked` from successful checks.
- Write `.last-checked.json` only after the full suite passes.
- Update `.githooks/verify-checks` to trust only matching content fingerprints and clean tracked/index state.
- Update `bin/dev merge` so check reuse happens after rebase and before fast-forward.
- Preserve intentional narrow-force paths, but remove force usage that existed only to compensate for the untrustworthy timestamp marker.
- Update `.gitignore` for the new local cache file and consider leaving old `.last-checked` ignored for compatibility/cleanup.

## 5. Untracked-file policy

Initial conservative policy proposal:

- Do not reject all untracked files globally; this repo frequently has local tool files/worktrees.
- Reject untracked files only in paths known to be consumed by checks if such paths are easy to enumerate.
- Otherwise document that v1 enforces tracked/index cleanliness plus content fingerprints, and create a follow-up yak for stricter untracked-input policy if needed.

This policy should be explicit in tests and output.

## 6. Documentation and ergonomics

- Update any contributor/development docs that mention `.last-checked`.
- Make reuse/rejection messages concise and actionable.
- Ensure failure modes are understandable when the record is missing, invalid JSON, stale schema, or missing fields.

# Definition of Done

- Timestamp mtimes are no longer used as proof of successful checks.
- `bin/dev check` writes a valid `.last-checked.json` only after a successful full check.
- `.githooks/verify-checks` accepts only a matching content-addressed record plus clean relevant tracked/index state.
- `bin/dev check --force` bypasses and refreshes the record.
- `bin/dev merge` can safely skip a redundant full suite only for the rebased candidate commit.
- ShellSpec tests cover reuse, mismatch, dirty/staged state, force, and merge reuse behaviour.
- Docs/comments mention the new marker and state that `checked_at` is informational only.

# Risks / Questions

- Environment/toolchain inputs are not fully content-addressed in v1. Decide what belongs in `check_version` now and what can wait.
- JSON tooling choice (`jq` vs Python) should match existing dev assumptions.
- Optional/missing file representation should support clear mismatch output.
- Untracked-file policy needs to balance safety and local developer noise.
