# Goal

Implement ADR 0024: replace timestamp-based `.last-checked` verification with a content-addressed, machine-readable local check record that `bin/dev check`, `.githooks/verify-checks`, and `bin/dev merge` can trust safely.

# Background

See `docs/adr/0024-content-addressed-check-verification.md`.

Current problem: `bin/dev check` writes an ignored timestamp marker. Hooks and `dev merge` can skip expensive checks based on mutable mtimes rather than the exact content and policy that passed.

# Desired Behaviour

A successful full `bin/dev check` writes `.last-checked.json` with a schema-versioned fingerprint of the verified workspace. Verification reuse is allowed only when the current workspace exactly matches the recorded fingerprint and the relevant workspace/index state is clean under the chosen policy.

`bin/dev check --force` ignores any existing record, reruns the suite, and overwrites the record on success.

`bin/dev merge` may reuse the record only after rebasing onto current `main`, so the fingerprint represents the candidate commit that would be fast-forwarded.

# Proposed Record v1

JSON, ignored locally, e.g. `.last-checked.json`:

- `schema_version: 1`
- `head`: `git rev-parse HEAD`
- `tree`: `git rev-parse HEAD^{tree}`
- `merge_base_main`: `git merge-base main HEAD` when `main` exists, otherwise explicit null/absent by deliberate policy
- `checked_at`: informational timestamp only; never proof
- `check_version`: explicit policy version string, bumped whenever the check policy changes in a way not captured by file hashes
- `dev_script_blob`: `git hash-object bin/dev`
- `verify_script_blob`: `git hash-object .githooks/verify-checks`
- `fingerprints` for relevant config/lock inputs initially:
  - `Cargo.lock`
  - `Cargo.toml`
  - `.cargo/config.toml` if present
  - `.pre-commit-config.yaml` if present
  - `.shellspec`

Use an explicit representation for optional/missing files, e.g. `{ "present": false }`, so mismatch messages are clear.

# Implementation Plan

## 1. Characterise existing behaviour

- Read `bin/dev`, `.githooks/verify-checks`, `dev merge`, and current ShellSpec coverage.
- Identify all current `.last-checked` reads/writes and any `.gitignore` entries.
- Keep this as a refactor of development scripts, not domain code.

## 2. Add failing ShellSpec coverage first

Add focused tests for the user-visible contract from ADR 0024:

- reuse when all fingerprints match,
- rejection when `HEAD` changes,
- rejection when `tree` changes / amended candidate differs,
- rejection when `Cargo.lock` changes,
- rejection when `bin/dev` changes,
- rejection when `.githooks/verify-checks` changes,
- rejection when optional fingerprinted files appear/disappear/change,
- rejection for dirty tracked files, including modifications and deletions,
- rejection for staged tracked files, including index-only changes, additions, deletions, and renames,
- explicit untracked-file policy behaviour,
- invalid JSON / stale schema / missing required fields are rejected with useful reasons,
- legacy `.last-checked` timestamp is ignored and cannot authorize reuse,
- `dev check --force` reruns and rewrites the record,
- `dev merge` rejects any pre-rebase record and reuses only a post-rebase record for the candidate commit.

Prefer checking concise output reasons such as `checks already verified for HEAD ...` or `check record rejected: Cargo.lock changed`.

## 3. Extract script helpers

Implement small shell helpers, likely in `bin/dev` and/or a shared helper if duplication emerges:

- compute current fingerprint JSON,
- write record atomically after successful full check,
- compare current fingerprint with record,
- print the first/most useful mismatch reason,
- detect dirty/staged tracked files without mtimes,
- detect untracked files under the explicit policy,
- reject invalid records before attempting reuse.

Keep JSON generation/parsing robust. Prefer `jq` if the repo already assumes it; otherwise use a small Python snippet to avoid silently adding a dev dependency.

## 4. Replace timestamp logic

- Stop writing `.last-checked` from successful checks.
- Ensure `.last-checked` is ignored as an authorization source everywhere.
- Write `.last-checked.json` only after the full suite passes.
- Update `.githooks/verify-checks` to trust only matching content fingerprints and clean state.
- Update `bin/dev merge` so check reuse happens after rebase and before fast-forward.
- Preserve intentional narrow-force paths, but remove force usage that existed only to compensate for the untrustworthy timestamp marker.
- Update `.gitignore` for the new local cache file and consider leaving old `.last-checked` ignored for compatibility/cleanup.

## 5. Untracked-file policy

Adopt an explicit v1 policy before implementation, then encode and test it. Proposed default after review:

- Reject untracked files in paths the verification suite is known to consume.
- Maintain an explicit allowlist for benign local/tooling paths if global untracked rejection is too noisy.
- Do not silently allow arbitrary untracked files without either a fingerprint, a rejection, or an allowlist reason.

If the consumed-path list is uncertain, choose the safer policy for v1 and add a follow-up yak for ergonomics.

## 6. Environment/toolchain policy

ADR 0024 names environmental inputs as harder follow-up territory. Decide explicitly before implementation:

- either include toolchain fingerprints in v1 (`rustc -Vv`, `cargo -V`, `shellspec --version`, cargo-audit if used, OS),
- or document that v1 relies on `check_version` plus file fingerprints and create follow-up work for environment fingerprints.

At minimum, define when `check_version` must be bumped.

## 7. Documentation and ergonomics

- Update any contributor/development docs that mention `.last-checked`.
- Make reuse/rejection messages concise and actionable, naming the mismatched field/path.
- Ensure failure modes are understandable when the record is missing, invalid JSON, stale schema, or missing fields.
- Document that `.last-checked.json` remains local/ignored and must not be committed.

# Definition of Done

- Timestamp mtimes are no longer used as proof of successful checks.
- Legacy `.last-checked` cannot authorize reuse.
- `bin/dev check` writes a valid `.last-checked.json` only after a successful full check.
- `.githooks/verify-checks` accepts only a matching content-addressed record plus clean state under the explicit dirty/staged/untracked policy.
- `bin/dev check --force` bypasses and refreshes the record.
- `bin/dev merge` can safely skip a redundant full suite only for the rebased candidate commit.
- ShellSpec tests cover reuse, mismatch, dirty/staged/untracked state, invalid records, legacy marker rejection, force, and merge reuse behaviour.
- Docs/comments mention the new marker, ignored/local nature, and that `checked_at` is informational only.

# 3-Way Review Findings

Reviewed by `deep-review-claude`, `deep-review-codex`, and `deep-review-gemini` on 2026-05-17.

Consensus / must-fix:

- The original untracked-file policy was too weak; the plan now requires an explicit rejection/allowlist policy.
- The plan must ensure the full ADR fingerprint set is present and tested, including optional files and `.githooks/verify-checks`.
- `dev merge` tests must prove a pre-rebase record is rejected and only a post-rebase candidate can be reused.
- Legacy `.last-checked` timestamp behavior must be removed/ignored everywhere, not left as a parallel trust path.
- Dirty/staged tests should include deletions, renames, and index-only changes.
- Rejection/reuse messages should name the changed fingerprint or state problem.

Additional review notes / follow-ups:

- Decide whether environment/toolchain fingerprints are v1 scope or explicitly deferred behind `check_version`.
- Test `tree` mismatches as well as `HEAD` mismatches.
- Keep `.last-checked.json` local/ignored; if any reviewer assumes it might be committed, clarify docs/tests that it must not be.
- Watch performance, but expected v1 file set is small.

# Risks / Questions

- Environment/toolchain inputs are not fully content-addressed unless included in v1. Decide what belongs in `check_version` now and what can wait.
- JSON tooling choice (`jq` vs Python) should match existing dev assumptions.
- Optional/missing file representation should support clear mismatch output.
- Untracked-file policy needs to balance safety and local developer noise, but must be explicit.
