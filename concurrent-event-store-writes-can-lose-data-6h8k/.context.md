## Problem

Two parallel `yx` processes (e.g. subagents in worktrees) writing to the same git event store can silently lose events. Events are stored as git commits on `refs/notes/yaks`, and worktrees share the same `.git` directory.

### Race condition

```
Agent A: reads refs/notes/yaks → commit X (parent)
Agent B: reads refs/notes/yaks → commit X (parent)
Agent A: creates commit Y (parent: X), updates ref → refs/notes/yaks = Y  ✅
Agent B: creates commit Z (parent: X), updates ref → refs/notes/yaks = Z  ✅
```

Agent A's commit Y is now orphaned — the ref points to Z (parent: X), so Y is unreachable. **Silent data loss.**

The idempotency guard (`has_event_id`) only prevents duplicate events, not concurrent writers.

### Possible fixes

1. **Compare-and-swap on ref update** — libgit2 supports this. The append would fail if the ref moved since we read it, and we'd retry (read new state, revalidate, re-append).
2. **File lock around append** — simple but coarser. A lockfile in `.git/` held during read-validate-append.
3. **Both** — CAS for correctness, lock to reduce contention.

### Impact

Medium — this is a real risk now that the parallel yak implementation skill has agents working in separate worktrees against the same repo.
