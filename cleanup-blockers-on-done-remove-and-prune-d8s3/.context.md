# Goal

Ensure active explicit blocker relationships are cleaned up when yaks are completed, removed, recursively removed, or pruned.

# Rules

- Marking a yak done resolves relationships where that yak is the blocker.
- Removing a yak resolves all active explicit relationships touching it, whether it is the blocker or target.
- Recursive remove cleans up relationships touching any yak in the removed subtree.
- Prune cleans up relationships touching any pruned done yak.
- Prefer explicit `BlockerRemoved` events over silently leaving stale projection state.

# Rules / Examples

```gherkin
Scenario: Direct done removes relationships for that blocker
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug"
  And I run yx blocker add deploy --by "fix bug"
  When I mark the yak "fix bug" as done
  Then the log should include a BlockerRemoved event for "deploy" blocked by "fix bug"
  And the yak "deploy" should no longer be blocked by "fix bug"
```

```gherkin
Scenario: Recursive done removes relationships for blockers inside the subtree
  Given I have a clean git repository
  And I add the yak "project"
  And I add the yak "A" under "project"
  And I add the yak "B" under "project"
  And I add the yak "deploy"
  And I add the yak "release"
  And I run yx blocker add deploy --by A
  And I run yx blocker add release --by B
  When I mark the yak "project" as done recursively
  Then the log should include a BlockerRemoved event for "deploy" blocked by "A"
  And the log should include a BlockerRemoved event for "release" blocked by "B"
  And "project", "A", and "B" should be done
```

```gherkin
Scenario: Removing a blocker yak removes relationships where it is the blocker
  Given "A" is explicitly blocked by "B"
  When I remove the yak "B"
  Then the log should include a BlockerRemoved event for "A" blocked by "B"
  And the log should include a Removed event for "B"
```

```gherkin
Scenario: Removing a blocked yak removes relationships where it is the target
  Given "A" is explicitly blocked by "B"
  When I remove the yak "A"
  Then the log should include a BlockerRemoved event for "A" blocked by "B"
  And the log should include a Removed event for "A"
```

```gherkin
Scenario: Removing a yak involved in multiple blocker relationships cleans them all
  Given "A" is blocked by "B"
  And "A" is blocked by "C"
  And "D" is blocked by "A"
  When I remove the yak "A"
  Then the log should include BlockerRemoved events for "A" blocked by "B", "A" blocked by "C", and "D" blocked by "A"
  And the log should include a Removed event for "A"
```

```gherkin
Scenario: Recursive remove cleans up active blockers touching the removed subtree
  Given "project" has children "A" and "B"
  And "deploy" is blocked by "A"
  And "B" is blocked by "external"
  When I remove "project" recursively
  Then the log should include a BlockerRemoved event for "deploy" blocked by "A"
  And the log should include a BlockerRemoved event for "B" blocked by "external"
  And the log should include Removed events for "project", "A", and "B"
```

```gherkin
Scenario: Prune cleans up active blockers touching pruned yaks
  Given done yak "old blocker" is still an active explicit blocker of "deploy"
  When I prune done yaks
  Then the log should include a BlockerRemoved event for "deploy" blocked by "old blocker"
  And the log should include a Removed event for "old blocker"
```

# Acceptance Notes

- After cleanup, list/show JSON must not retain `blocked_by` entries pointing to removed or pruned yaks.
- Event order should be understandable: cleanup events before or alongside removal/state events, but tests should assert the important events rather than over-specifying ordering unless order matters to projection.
- Idempotency from the idempotent-command slice should hold: cleanup should not emit duplicate `BlockerRemoved` events for the same active relationship.

# Test Guidance

Use Gherkin for command flows and log/projection assertions. Add lower-level tests for computing the relationships touched by a set of yak IDs.
