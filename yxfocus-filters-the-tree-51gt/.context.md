# YX_FOCUS filters the tree

## Intent

Allow an agent to work in one area of the yak tree as though that area is the root, without being distracted by unrelated yaks.

`YX_FOCUS` is an environment variable containing the exact yak id to focus on.

```bash
YX_FOCUS=<yak-id> yx list
```

If `YX_FOCUS` is set to an unknown id, commands should fail immediately with an error.

## Scope / access control

The focused view contains exactly:

- ancestors of the focused yak, for context
- the focused yak itself
- all descendants of the focused yak

Anything outside that rendered focused tree is inaccessible. Commands should be prevented from operating on hidden yaks, with an error that says the yak is outside `YX_FOCUS` rather than merely “not found”.

Visible ancestors are actionable, not read-only. For example, if focused on `B`, commands such as `yx show A`, `yx done A`, or `yx add --parent A ...` are allowed when `A` is a visible ancestor.

## Command behaviour

All applicable commands should respect `YX_FOCUS`, ideally via one central tree pruning/filtering mechanism.

- `yx list` shows the pruned focused tree.
- `yx show <hidden-yak>` errors because the yak is outside `YX_FOCUS`.
- `yx add <name>` with no explicit parent creates a child of the focused yak, as though the focused yak were the root.
- `yx add --parent <visible-yak> <name>` is allowed.
- `yx add --parent <hidden-yak> <name>` is rejected.

Unset `YX_FOCUS` to bypass focus. There should be no `--no-focus` flag.

## ID resolution

`YX_FOCUS` must be an exact yak id. No fuzzy matching or id prefix matching. If it is not exact, error.

## UI example

Full tree:

```text
Project
├─ A
│  ├─ B
│  │  ├─ E
│  │  └─ F
│  └─ C
│     └─ G
└─ D
   └─ H
```

With:

```bash
YX_FOCUS=B
```

Focused rendering draft:

```text
Project
├─ A
┆  ├─ B
   ┆  ├─ E
      └─ F
```

Meaning:

- `Project → A → B` is the visible ancestor path.
- `E` and `F` are visible because they’re under focused yak `B`.
- the dotted marker under `A` means “A has hidden child branches outside focus” — e.g. `C`.
- the dotted marker under `Project` means “Project has hidden child branches outside focus” — e.g. `D`.

UI rule:

- use `├─` rather than `└─` when a visible node has hidden siblings at that level
- on subsequent descendant lines, render `┆` in that ancestor’s indentation column to indicate pruned siblings
- render the dotted marker only when one or more sibling branches are hidden
- omit any hidden marker when there are no hidden siblings
- keep the marker to a single character; no ellipsis or label by default
