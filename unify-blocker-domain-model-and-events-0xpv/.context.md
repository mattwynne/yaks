# Goal

Unify manual blockers and yak-to-yak blockers under one domain/event model, and clean up the blocker-cycle validation language/model underneath.

# Decision

Model both manual blockers and yak blockers as `Blocker`s with a `BlockerSource`, rather than maintaining separate event families and separate aggregate maps.

Also replace user-facing "blocker cycle" language with "circular dependency". Do not make cycle errors expose internal distinctions such as "through hierarchy" unless there is a clear user need.

This should simplify terminology, compaction snapshots, view construction, cycle validation, and future maintenance.

# Current Problem

Current aggregate state splits blockers into:

```rust
blockers: HashMap<TargetId, HashMap<BlockerId, Option<Reason>>>
manual_blockers: HashMap<TargetId, Reason>
```

Then `active_blockers()` recombines both into an `ActiveBlocker` view:

```rust
ActiveBlocker { kind: Yak | Manual, id, reason }
```

Current events are also split:

- `BlockerAdded/Updated/Removed` for yak-to-yak blockers
- `ManualBlockerAdded/Updated/Removed` for manual/external blockers

This creates terminology and modelling friction:

- manual blockers are blockers, but not represented by the same domain/event type
- `ActiveBlocker` is a computed polymorphic view rather than the core model
- compaction/snapshot code can easily forget aggregate-level blocker state
- manual blocker identity/multiplicity is over-shaped by storage/events even though current UX only cares about setting/clearing one manual reason

Cycle validation also has awkward language/modeling:

- user-facing errors say "blocker cycle", which is graph/implementation language
- hierarchy-involved cycles are described as "through hierarchy", but Matt does not currently see a need to expose that distinction to users
- `path_to_blocker()` returns `Option<(Vec<YakId>, bool)>`; the boolean means `uses_hierarchy`, which is obscure and may not be needed if the distinction only fed user-facing copy

# Target Model

Introduce a unified blocker type, e.g.

```rust
pub struct Blocker {
    pub source: BlockerSource,
    pub reason: Option<String>,
}

pub enum BlockerSource {
    Yak(YakId),
    Manual,
}
```

Manual blockers do not need identity for now. Current UX can keep one manual blocker by treating `BlockerSource::Manual` as unique per target; that is a command/use-case policy, not a reason to maintain a separate event family.

Possible aggregate storage:

```rust
blockers_by_target: HashMap<YakId, Vec<Blocker>>
```

or a more lookup-friendly equivalent, as long as the public/domain concept is one blocker collection per target.

Domain semantics:

- `BlockerSource::Yak(id)` participates in blocker/circular-dependency validation.
- `BlockerSource::Manual` does not participate in blocker/circular-dependency validation.
- Both affect readiness/start/done guards.
- Removing/done/pruning a yak cleans up blockers whose source is `Yak(id)` or whose target is removed.
- Manual blocker set/update/clear remains supported through `yx blocker add <yak> --reason ...` and `yx blocker rm <yak> --manual`.

# Cycle Validation Language and Model

Use user-facing language like:

```text
Cannot add blocker: this would create a circular dependency.
```

or, where useful:

```text
Adding "legal approval" as a blocker for "security review" would create a circular dependency: legal approval -> deploy release -> security review -> legal approval
```

Avoid asserting or exposing "through hierarchy" in feature scenarios unless implementation work uncovers a genuine user-facing need for that distinction.

Internally, prefer a named type over tuple booleans. If hierarchy usage is no longer needed, keep it simple:

```rust
pub struct BlockerPath {
    pub yaks: Vec<YakId>,
}
```

If implementation proves the relationship mix is still needed for domain logic, make it explicit with a named type rather than a `bool`; but do not introduce that complexity just for error-message wording.

# Unified Events

Replace or wrap the current split event family with unified blocker events:

```rust
BlockerAdded {
    target: YakId,
    blocker: Blocker,
}

BlockerUpdated {
    target: YakId,
    blocker: Blocker,
}

BlockerRemoved {
    target: YakId,
    source: BlockerSource,
}
```

Exact struct shape can vary; the key is that yak blockers and manual blockers use the same event names and semantics.

Prefer explicit serialized source kind over an ambiguous empty/null blocker id. For example:

```text
BlockerAdded "deploy" "yak" "security-review" "needs sign-off"
BlockerAdded "deploy" "manual" "waiting for credentials"
BlockerRemoved "deploy" "manual"
BlockerRemoved "deploy" "yak" "security-review"
```

Keep backwards compatibility for existing events:

- old `BlockerAdded target blocker reason` parses as source `Yak(blocker)`
- old `BlockerUpdated target blocker reason` parses as source `Yak(blocker)`
- old `BlockerRemoved target blocker` parses as source `Yak(blocker)`
- old `ManualBlockerAdded target reason` parses/applies as unified manual blocker added/set
- old `ManualBlockerUpdated target reason` parses/applies as unified manual blocker updated/set
- old `ManualBlockerRemoved target` parses/applies as unified manual blocker removed

# Relationship to Compaction

This should compose with `compact whole YakMap snapshot`:

- `YakMapSnapshot` should include active blockers using the unified `Blocker` model.
- Replaying a compacted event reconstructs the same blockers/readiness as before compaction.
- Preserve compatibility with the snapshot format introduced by `compact whole YakMap snapshot`.

# Acceptance / Test Coverage

Start with existing blocker feature scenarios to ensure behaviour remains correct, but update error-message assertions from "blocker cycle" / "through hierarchy" to clearer "circular dependency" language.

Do not make the `a`, `b`, `c` examples vivid in this yak. Leave example naming cleanup to `make blocker feature examples vivid`.

Add or preserve coverage for:

- manual blockers and yak blockers both appear in JSON `blocked_by` with kind/source
- manual blockers and yak blockers both affect readiness and workflow guards
- yak blockers still reject circular dependencies
- manual blockers do not participate in circular-dependency validation
- old split event formats still replay correctly
- compaction snapshot preserves both manual and yak blockers using the current `YakMapSnapshot` compatibility path

# Open Implementation Choice

Suggested order:

1. Update cycle-validation wording/tests from "blocker cycle" to "circular dependency" without changing scenario example names.
2. Replace tuple-bool blocker path returns with a named `BlockerPath` type; only keep relationship-kind information if domain logic genuinely needs it.
3. Introduce unified domain types and compatibility parsing while keeping behaviour stable.
4. Adapt `YakMapSnapshot` / compaction compatibility to the unified model.
5. Optionally remove/retire old manual-specific event variants once compatibility is safely handled.

# Definition of Done

- Manual and yak blockers are represented by one coherent domain model.
- Event names/semantics are unified around `BlockerAdded/Updated/Removed` with a source/kind.
- Existing repositories with old manual blocker events remain readable.
- Existing compacted snapshots remain readable.
- User-facing cycle errors use "circular dependency", not "blocker cycle".
- Feature examples are not made vivid here; that remains scoped to `make blocker feature examples vivid`.
- The `ActiveBlocker` naming issue is resolved, either by removal or by renaming to match the unified model.
- Tuple boolean path modelling is removed or replaced with a named type.
