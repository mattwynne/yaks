# Goal

Validate `yx mv` operations against the effective blocker graph so moves cannot introduce blocker cycles, while allowing moves that safely replace explicit blockers with hierarchy.

# Effective Graph Rules

- Explicit blocker: `yx blocker add A --by B` creates edge `B → A`.
- Hierarchy blocker: descendant blocks ancestor.
- Moving changes hierarchy edges, so the effective graph after the move must be checked.
- Failed moves emit no `Moved` event and no blocker cleanup events.

# Rules / Examples

## Existing hierarchy cycle protection remains

```gherkin
Scenario: Moving a yak under its own descendant is rejected
  Given I have a clean git repository
  And I add the yak "parent"
  And I add the yak "child" under "parent"
  When I try to move "parent" under "child"
  Then the command should fail
  And the error should explain that a yak cannot be moved under its own descendant
  And the log should not include a Moved event for "parent"
```

## Move can replace explicit blocker with hierarchy when direction matches

```gherkin
Scenario: Moving a blocker under the yak it blocks replaces explicit blocker with hierarchy
  Given I have a clean git repository
  And I add the yak "A"
  And I add the yak "B"
  And I run yx blocker add A --by B
  When I move "B" under "A"
  Then the command should succeed
  And the log should include a BlockerRemoved event for "A" blocked by "B"
  And the log should include a Moved event for "B" under "A"
  And "B" should still block "A" through hierarchy
  And "A" should have no explicit blocked_by entry for "B"
```

## Move that creates an effective cycle is rejected

```gherkin
Scenario: Moving a blocked yak under its blocker is rejected as a cycle
  Given yaks "A" and "B" exist
  And I run yx blocker add A --by B
  When I try to move "A" under "B"
  Then the command should fail
  And the error should explain that the move would create a blocker cycle involving "A" and "B"
  And the log should not include a Moved event for "A"
```

```gherkin
Scenario: Moving an ancestor under an explicit blocker is rejected when it creates a cycle
  Given I have a clean git repository
  And I add the yak "project"
  And I add the yak "A" under "project"
  And I add the yak "B"
  And I run yx blocker add A --by B
  When I try to move "project" under "B"
  Then the command should fail
  And the error should mention the blocker path involving "B", "A", and "project"
  And the log should not include a Moved event for "project"
```

# Acceptance Notes

- Move validation must evaluate the effective graph after the proposed move.
- If the proposed hierarchy makes an active explicit blocker redundant in the same direction, the move may succeed and should emit `BlockerRemoved` for the redundant explicit relationship.
- Moves that would create opposite-direction hierarchy edges relative to active blockers must fail.
- Errors should include useful path/cycle information and mention hierarchy when it is involved.
- Keep this slice about moves; `blocker add` cycle rejection belongs in `reject blocker cycles on add`.

# Test Guidance

Use Gherkin for the user-visible move flows and log assertions. Add domain/unit tests for graph transformation/checking, especially ancestor/subtree cases and the explicit-to-hierarchy replacement case.
