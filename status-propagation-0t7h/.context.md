# Status

Needs redesign before implementation.

This yak was written when Disco `blocked` was expected to map to a new Yaks workflow state `stuck`. That assumption is now stale: Yaks workflow state is intentionally only `todo | wip | done`, with blocked/readiness represented separately by blockers and derived readiness.

# Original Goal

Add automatic status propagation rules to match Disco discovery tree conventions.

# Revised Questions

Before implementing, decide how Disco status propagation maps onto the current Yaks model:

- Should Disco `blocked` become a manual blocker / readiness presentation rather than a workflow state?
- Should parent "blocked" presentation be derived from incomplete/blocked descendants rather than persisted?
- Should `doing`/`wip` propagation be presentation-only rather than mutating parent workflow state?
- How does this interact with Yaks' current rule that parent progress/readiness is derived from children?

# Do Not Do

Do not add a `stuck` workflow state as a prerequisite without a fresh design decision/ADR that supersedes the current workflow-state/readiness model.
