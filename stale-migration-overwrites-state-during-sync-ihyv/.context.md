## Bug: Stale migration overwrites state during sync

### Observed behaviour
On a machine with an old binary (old schema version) and stale local
yak state, running `yx sync` after upgrading the binary:
1. Migration runs first (main.rs:633), creates a Migrated event
   with stale snapshots and a current timestamp
2. Sync merges the Migrated event with origin's correct events
3. Migrated event sorts LAST (newest timestamp) in the merge
4. During replay, the Migrated commit becomes the tip of the ref
5. get_all_events() hits the Migrated boundary first, reads stale
   snapshots, stops — all real events below it are invisible

Result: entire yak state replaced with stale data from the old machine.

### Root cause
Migration runs before sync in main.rs:633. compact_ref() in
migration.rs:173 creates a "Migrated" boundary event from whatever
state is currently in the local tree. If local state is stale, the
Migrated event captures stale state.

The merge code in mod.rs:86-88 only handles YakEvent::Compacted for
orphan reordering. Migrated events pass through as ordinary events,
sorted by timestamp.

### Key code locations
- migration.rs:173 compact_ref() — creates the Migrated commit
- main.rs:633 — migration runs before any command
- sync.rs:67 sync_with_remote() — the sync flow
- mod.rs:53 merge_event_streams() — the merge logic
- git.rs:386 get_all_events() — walks history, stops at boundaries

### Relevant ADRs
- ADR 0009: Compacted event design (orphan reordering for Compacted)
- ADR 0011: Schema versioning and sync compatibility
- ADR 0012: Compact after migration to hide pre-migration history
- ADR 0020: UUID for migration compaction events

### Reproduction test
A @fullstack @wip cucumber test has been added in sync.feature:
"Bob's stale local yaks don't replace Alice's after migration
and sync" — with step definition v1_yak_in_repo in steps.rs.
Committed to main.

### Fix approaches explored

**Approach 1 (too aggressive): Strip Migrated from merge entirely**
Prevents the overwrite bug BUT causes bob to lose his local yak
"buy biscuits" because it only exists in the Migrated event's
snapshots. The underlying v1 events are hidden behind the
migration boundary.

**Approach 2: Convert Migrated snapshots to Added events in merge**
Decompose each Migrated event's snapshots into synthetic Added
events during merge. Yaks survive without destructive clear-all.

**Approach 3: Migration creates Compacted instead of Migrated**
Existing orphan reordering would apply, but ADR 0009 notes the
gap with multiple Compacted events — only the first is handled.

**Approach 4: Don't create boundary events at all**
Migration transforms trees without adding a checkpoint.
get_all_events() would need old-format fallback paths, which
ADR 0012 explicitly rejected.

**Approach 5: Move migration inside sync flow, after pulling**
Boundary would capture merged state, not stale local state.
Tricky because get_all_events() needs current schema to read.

**Approach 6 (LEADING): Lazy migration — upgrade old trees on
the fly during read**
Eliminate the Migrated boundary event entirely. Each tree already
carries .schema-version, so get_all_events() knows when it hits
an old-format tree. Instead of rewriting history upfront, apply
migrations lazily at read time:
- No Migrated event, no compact_ref() during migration
- Migration still upgrades the TIP tree on startup (so new
  appends are in current format)
- get_all_events() applies the migration chain to older trees
  when walking past the tip into old commits
- ADR 0012's concern about fallback code accumulation is
  addressed differently: the migration chain IS the fallback,
  invoked at read time instead of write time
- Kills this entire class of bug at the root — no boundary
  event means nothing to corrupt during sync

### Open design question: compaction after lazy migration
If we adopt approach 6, should migration still trigger a
compaction? Trade-offs to consider:

**Compacting after migration (current behaviour minus Migrated):**
+ Faster subsequent reads — don't re-migrate old trees every time
+ Smaller working set — old events are hidden below boundary
- Compaction captures local state as a snapshot, which has the
  same "stale state during sync" risk if the Compacted event
  enters the merge with a "now" timestamp
- Couples migration to compaction (ADR 0012 consequence)

**NOT compacting after migration:**
+ Simpler — migration just upgrades the tip tree, done
+ No snapshot event means no sync corruption risk
+ Compaction remains a separate, user-triggered operation
- Slower reads on first run after upgrade — every
  get_all_events() call walks and migrates old trees until
  the user runs yx compact
- Could be mitigated by caching / rebuilding the projection
  once on startup (which already happens: needs_projection_reset)

Leaning toward NOT compacting after migration. The projection
rebuild on startup already handles the "first run after upgrade"
cost. Compaction can remain a separate user choice for perf.
