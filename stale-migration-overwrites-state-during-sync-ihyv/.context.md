## Bug: Stale migration overwrites state during sync

### Observed behaviour
On a machine with an old binary (old schema version) and stale local
yak state, running `yx sync` after upgrading the binary:
1. Migration runs first (main.rs:633), creates a Migrated event
   with stale snapshots and a current timestamp
2. Sync merges the Migrated event with origin's correct events
3. Migrated event sorts LAST (newest timestamp) in the merge
4. During replay, the Migrated commit becomes the tip of the ref
5. get_all_events() hits the Migrated boundary first, reads stale
   snapshots, stops — all real events below it are invisible

Result: entire yak state replaced with stale data from the old machine.

### Root cause
Migration runs before sync in main.rs:633. compact_ref() in
migration.rs:173 creates a "Migrated" boundary event from whatever
state is currently in the local tree. If local state is stale, the
Migrated event captures stale state.

The merge code in mod.rs:86-88 only handles YakEvent::Compacted for
orphan reordering. Migrated events pass through as ordinary events,
sorted by timestamp.

### Key code locations
- migration.rs:173 compact_ref() — creates the Migrated commit
- main.rs:633 — migration runs before any command
- sync.rs:67 sync_with_remote() — the sync flow
- mod.rs:53 merge_event_streams() — the merge logic
- git.rs:386 get_all_events() — walks history, stops at boundaries

### Relevant ADRs
- ADR 0009: Compacted event design (orphan reordering for Compacted)
- ADR 0011: Schema versioning and sync compatibility
- ADR 0012: Compact after migration to hide pre-migration history
- ADR 0020: UUID for migration compaction events

### Fix approaches explored

**Approach 1 (too aggressive): Strip Migrated from merge entirely**
Current state of the code. Prevents the overwrite bug BUT causes
bob to lose his local yak "buy biscuits" because it only exists
in the Migrated event's snapshots. The underlying v1 events are
hidden behind the migration boundary.

Test result: bob gets "make the tea" but loses "buy biscuits".

**Approach 2: Convert Migrated snapshots to Added events in merge**
During merge, decompose each Migrated event's snapshots into
synthetic Added events. The yaks survive without the destructive
clear-all semantics. The dedup-by-event-id in merge handles
duplicates naturally. This preserves the local Migrated boundary
for read optimisation while preventing sync corruption.
LEADING CANDIDATE — not yet implemented.

**Approach 3: Migration creates Compacted instead of Migrated**
Then existing orphan reordering handles it. But ADR 0009 notes
the gap with multiple Compacted events — only the first is handled.
A stale Compacted with "now" timestamp would still sort last.

**Approach 4: Don't create boundary events at all**
Migration transforms trees without adding a checkpoint.
get_all_events() would need old-format fallback paths, which
ADR 0012 explicitly rejected.

**Approach 5: Move migration inside the sync flow, after pulling**
So the boundary captures merged state, not stale local state.
Tricky because get_all_events() needs current schema to read.

### Open design question
Should Migrated events exist in the store at all? They're a local
read optimisation (hiding pre-migration history) but have
destructive clear-all semantics that are dangerous during sync.
