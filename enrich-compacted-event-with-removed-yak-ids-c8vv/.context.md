# Goal

Add `removed_yak_ids: Vec<YakId>` to the `Compacted` event so the merge algorithm can distinguish between:
- A genuinely new yak from an offline peer (should be preserved as orphan)
- A stale `Added` event for a yak that was deliberately removed before compaction (should be dropped)

# Key code changes
- `Compacted` variant gains `removed_yak_ids` field
- `compact()` collects IDs of all yaks that have `Removed` events in the pre-compaction stream
- `merge_event_streams()` orphan logic checks: if orphan's yak_id is in `removed_yak_ids`, drop it instead of moving it after Compacted
- Git tree serialisation needs to persist removed IDs (e.g. a `.removed-yaks` blob)

# Depends on
This is independent of the Migrated event change, but together they cover both cases:
- Migrated prevents divergent migration snapshots
- This fixes the merge logic for user-triggered compaction

# Scenarios

## sync.feature

New scenario — the zombie bug regression test. This would fail today and pass after the fix:

```gherkin
Rule: Removed yaks stay removed after compaction and sync

  Example: Alice's removed yak doesn't reappear when Bob has stale events
    Given a git clone of origin called alice
    And a git clone of origin called bob
    And alice has a yak called "make the tea"
    And alice has a yak called "buy biscuits"
    And alice has synced yaks
    And bob has synced yaks
    And alice has removed the yak "buy biscuits"
    And alice has compacted yaks
    And alice has synced yaks
    When bob syncs yaks
    Then bob should not have a yak called "buy biscuits"
    And bob should have a yak called "make the tea"
```

The existing scenario "Bob's unsynced yak survives Alice's compaction" (under "Unsynced events survive compaction by another peer") remains unchanged — it tests the happy orphan case where a genuinely new yak is preserved.
