# Story

Prevent invalid blocker relationships when explicit blockers interact with hierarchy and moves.

As a yak user, I want blocker relationships and hierarchy moves to preserve an acyclic effective blocking graph, so that readiness remains understandable and yaks never deadlock each other.

# Rule: Effective blocker graph is directional and acyclic

Direction:

- `yx blocker add A --by B` means `B` blocks `A`, represented as edge `B → A`.
- hierarchy is an implicit dependency/blocker: child/descendant blocks parent/ancestor.
- explicit `BlockerAdded` events add explicit blocker edges.
- implicit hierarchy blockers and explicit blocker events together form the effective blocking graph.
- cycles are never allowed in the effective blocking graph.

# Rule: Adding an explicit blocker must not create a cycle

## Examples

- Self-blocking is rejected:
  - Given yak `A`
  - When `yx blocker add A --by A`
  - Then it fails and emits no `BlockerAdded` event.
  - Error should explain that a yak cannot block itself.
- Mutual explicit cycle is rejected:
  - Given `A` is blocked by `B`
  - When `yx blocker add B --by A`
  - Then it fails and emits no `BlockerAdded` event.
  - Error should mention the cycle, e.g. `A already depends on B` / `would create cycle: A -> B -> A`.
- Longer explicit cycle is rejected:
  - Given `A` is blocked by `B`, and `B` is blocked by `C`
  - When `yx blocker add C --by A`
  - Then it fails and emits no `BlockerAdded` event.
  - Error should mention the dependency path that would become cyclic.
- Hierarchy plus explicit cycle is rejected:
  - Given `child` is under `parent`
  - When `yx blocker add child --by parent`
  - Then it fails and emits no `BlockerAdded` event.
  - Error should explain that `child` already blocks `parent` through hierarchy.
- Multi-ancestor hierarchy plus explicit cycle is rejected:
  - Given `grandchild` is under `child`, and `child` is under `parent`
  - When `yx blocker add grandchild --by parent`
  - Then it fails and emits no `BlockerAdded` event.
  - Error should mention the hierarchy path.
- Redundant hierarchy blocker is a no-op success:
  - Given `child` is under `parent`
  - When `yx blocker add parent --by child`
  - Then it succeeds, emits no event, and advises that `child` already blocks `parent` through hierarchy.

# Rule: Moving can replace an explicit blocker with hierarchy when the direction matches

Moving changes hierarchy, which changes implicit blocking edges.

If a move would make an active explicit blocker relationship represented by hierarchy in the same direction, the move can succeed by removing the explicit blocker relationship and relying on hierarchy afterwards.

## Examples

- Existing hierarchy cycle remains rejected:
  - Given `child` is under `parent`
  - When `yx mv parent --under child`
  - Then it fails.
  - Error should continue to explain that a yak cannot be moved under its own descendant.
- Moving a blocker under the yak it blocks replaces explicit blocker with hierarchy:
  - Given `A` is explicitly blocked by `B` (`B → A`)
  - When `yx mv B --under A`
  - Then it succeeds
  - And emits `BlockerRemoved(A, B)`
  - And emits `Moved(B, under A)`
  - And `B` still blocks `A`, now implicitly through hierarchy.
- Moving a blocked yak under its blocker is rejected as a cycle:
  - Given `A` is explicitly blocked by `B` (`B → A`)
  - When `yx mv A --under B`
  - Then it fails, because hierarchy would add `A → B` and create a cycle.
  - Error should explain that the move would create a blocker cycle.
  - And no `Moved` event is emitted.

# Rule: Moving an ancestor under an explicit blocker is rejected when it creates a cycle

## Example

- Moving ancestor under blocker creates a cycle:
  - Given `A` is under `project`
  - And `A` is explicitly blocked by `B` (`B → A`)
  - When `yx mv project --under B`
  - Then it fails, because the move would create `B → A → project → B`.
  - Error should explain the dependency path/cycle, including the hierarchy relationship.
  - And no `Moved` event is emitted.

# Rule: Removing a yak resolves active explicit blocker relationships involving it

Removing either side of an active explicit blocker relationship should emit `BlockerRemoved` events before removing the yak. The current projection should not retain active blockers pointing to or from removed yaks.

## Examples

- Removing a blocker yak removes relationships where it is the blocker:
  - Given `A` is explicitly blocked by `B` (`B → A`)
  - When `yx rm B`
  - Then it emits `BlockerRemoved(A, B)`
  - And emits `Removed(B)`.
- Removing a blocked yak removes relationships where it is the target:
  - Given `A` is explicitly blocked by `B` (`B → A`)
  - When `yx rm A`
  - Then it emits `BlockerRemoved(A, B)`
  - And emits `Removed(A)`.
- Removing a yak involved in multiple blocker relationships removes all active explicit relationships involving it:
  - Given `A` is blocked by `B` and `C`
  - And `D` is blocked by `A`
  - When `yx rm A`
  - Then it emits `BlockerRemoved(A, B)`, `BlockerRemoved(A, C)`, and `BlockerRemoved(D, A)`
  - And emits `Removed(A)`.

# Error Message Guidance

Cycle/rejection errors should be actionable. Prefer mentioning:

- the command would create a blocker/dependency cycle
- the relevant yaks in the cycle/path
- whether hierarchy is involved when that is the surprising part

Exact wording can be refined during implementation, but acceptance tests should assert the key information rather than brittle full strings.
