# Goal

Use example mapping to design and specify blocker edge cases before implementing the full matrix.

# Why

Explicit blocker relationships interact with hierarchy. The effective blocking graph includes:

- implicit hierarchy blockers: children/descendants block ancestors for readiness
- explicit blockers: `BlockerAdded(target, blocker)` active until `BlockerRemoved`

Cycles must never be allowed. Moves can create cycles after relationships already exist, so move validation needs careful examples.

# Example Mapping Topics

## Cycles

- self-blocking
- mutual explicit cycle
- longer explicit cycle
- child/parent mixed cycle
- multi-ancestor blocking cycle
- redundant explicit blocker that duplicates hierarchy

## Moves

- moving a blocker under the yak it blocks
- moving a blocked yak under its blocker
- moving subtrees with blockers pointing into the subtree
- moving subtrees with blockers pointing out of the subtree
- moving yaks such that an existing explicit blocker becomes an ancestor/descendant relationship
- ensuring existing “cannot move under descendant” protection still works

## Deletes / Prune

- removing a yak that blocks other yaks
- removing a yak that is blocked by other yaks
- pruning a done yak that used to be a blocker
- whether removal should emit `BlockerRemoved` events or whether projection should ignore relationships to removed yaks

## Duplicates / No-ops

- duplicate explicit add with no change: success, no event, advice
- duplicate explicit add with same reason: success, no event, advice
- duplicate explicit add with changed reason: `BlockerUpdated`
- explicit add redundant with hierarchy: success, no event, advice

# Expected Output

Before coding the full edge-case implementation, update this yak or create follow-up yaks with concrete Gherkin scenarios for the agreed behaviour.

At minimum, define which edge cases belong in the first vertical slice and which can be deferred safely.
