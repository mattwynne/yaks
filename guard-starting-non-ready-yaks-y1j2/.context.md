# Goal

Make non-recursive `yx start` respect readiness/blockers.

# Decision

`yx start <yak>` should only be allowed when the yak is ready.

Ready means:

- stored workflow state is `todo`
- no incomplete child/descendant blockers prevent direct work
- no active explicit blockers from `BlockerAdded` events

# Scope Note

This slice intentionally guards only non-recursive `yx start`. Existing `yx start --recursive` bulk state behavior is preserved for now, including starting a parent and its todo descendants even though the parent would not be ready for a direct start. Recursive readiness semantics are deferred to the follow-up yak `clarify recursive start readiness semantics`.

# Behaviour

- Starting a yak blocked by explicit blockers fails clearly.
- Starting a parent with incomplete children fails clearly.
- Failed start emits no state-change event.
- The error should explain what blocks the yak.
- Recursive start remains a bulk state change for this slice.

# Acceptance Scenarios

## Explicit blocker prevents start

```gherkin
Scenario: A yak blocked by another yak cannot be started
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug"
  And I run yx blocker add deploy --by "fix bug"
  When I try to start "deploy"
  Then the command should fail
  And the error should contain "blocked by fix bug"
  And the yak "deploy" should have state "todo"
```

## Incomplete child prevents parent start

```gherkin
Scenario: A parent with incomplete children cannot be started
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug" under "deploy"
  When I try to start "deploy"
  Then the command should fail
  And the error should contain "blocked by incomplete child fix bug"
  And the yak "deploy" should have state "todo"
```

## Recursive start preserved

```gherkin
Scenario: Recursive start keeps existing bulk state behavior
  Given I have a clean git repository
  And I add the yak "parent"
  And I add the yak "child" under "parent"
  When I start "parent" recursively
  Then both "parent" and "child" should be wip
```

# Override Design

Consider but do not assume an override such as:

```sh
yx start deploy --remove-blockers
```

If implemented:

- it should emit `BlockerRemoved` events for explicit blockers before/with the state change to `wip`
- it probably should not remove hierarchy blockers; children should be completed or moved instead
- it needs Gherkin coverage for the event sequence

This may be part of the blocker vertical slice or a follow-up depending on complexity.
