# Goal

Prevent users from marking a yak done while it is still blocked by active explicit blockers.

# Scope

Focus on `yx done <yak>` / non-recursive completion of the target yak. Keep existing incomplete-child protection intact. Do not design a blast-through override in this slice.

# Rules / Examples

## Explicit blockers prevent completion

```gherkin
Scenario: A yak with an active explicit blocker cannot be marked done
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug"
  And I run yx blocker add deploy --by "fix bug"
  When I try to mark the yak "deploy" as done
  Then the command should fail
  And the error should explain that "deploy" is blocked by "fix bug"
  And the yak "deploy" should have state "todo"
  And the log should not include a state change for "deploy" to done
```

## Resolved blockers allow completion

```gherkin
Scenario: A yak can be completed after its explicit blocker is resolved
  Given "deploy" is explicitly blocked by "fix bug"
  And I mark the yak "fix bug" as done
  When I mark the yak "deploy" as done
  Then the command should succeed
  And the yak "deploy" should have state "done"
```

## Existing child-blocker protection remains

```gherkin
Scenario: A parent with incomplete children still cannot be marked done non-recursively
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug" under "deploy"
  When I try to mark the yak "deploy" as done
  Then the command should fail
  And the error should mention the incomplete child "fix bug"
  And the yak "deploy" should not have state "done"
```

# Acceptance Notes

- Active explicit blockers block completion just as they block readiness/start.
- Failed completion emits no state event and no blocker cleanup events for the target yak.
- Completing the blocker itself is handled by the cleanup slice: that should remove relationships where the completed yak is the blocker.
- Recursive completion semantics may need to interact with this later; do not add a blocker-clearing override without explicit design and Gherkin.

# Test Guidance

Use Gherkin for user-visible command failures and state/log assertions. Add unit tests if the completion use case gets a shared readiness/blocker guard.
