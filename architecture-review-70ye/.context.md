# Architectural Assessment: Yaks

## Executive Summary

This is a **remarkably well-architected** small codebase. At ~16,500 lines of Rust with ~2,000 lines of Gherkin, it demonstrates the hand of someone who deeply understands both domain-driven design and pragmatic software delivery. The architecture is overengineered for the problem size, but deliberately and knowingly so, and the investment is paying off in testability and evolvability.

---

## Strengths

### 1. Genuine Hexagonal Architecture (not just cosmetic)

The ports-and-adapters boundary is real, not decorative. Domain types (`YakId`, `Name`, `Slug`, `Yak`, `YakEvent`) live in `domain/` with zero infrastructure dependencies. Port traits (`EventStore`, `ReadYakStore`, `DisplayPort`, `InputPort`) define clean contracts. Every adapter has an in-memory test double. The `projections/write_to_yak_store.rs` blanket impl (`impl<T: WriteYakStore> EventListener for T`) is an elegant piece of design — any storage backend automatically becomes a projection listener.

This isn't cargo cult architecture. The boundaries serve a real purpose: the Cucumber tests run in two modes (full-stack CLI and in-process), exercising the same features at different layers. That's a powerful testing strategy.

### 2. Exemplary BDD / Living Documentation

The `.feature` files are genuinely good. They use Rules to group scenarios by business concern, names are declarative ("Cannot mark a parent as done while children are incomplete"), and they avoid implementation leakage. The dual-world test strategy (`FullStackWorld` / `InProcessWorld`) with a shared `TestWorld` trait is sophisticated and well-executed. ~163 scenarios across 20 feature files provide strong behavioral coverage.

### 3. Disciplined Event Sourcing

The event model is clean: `Added`, `Removed`, `Moved`, `FieldUpdated`, `Compacted`. Events carry metadata (author, timestamp, event_id). The CRDT-style merge in `merge_event_streams` handles the tricky case of post-compaction orphan events. Backward-compatible event parsing (legacy `Renamed` → `FieldUpdated`) shows thoughtful evolution. Schema migration (v1→v2→v3→v4) is well-structured with contract tests.

### 4. ADRs and Design Documentation

10 ADRs that actually explain the *why*. The `src/README.md` has a clear "How a Command Flows" diagram. The CLI design philosophy doc, implementation plans, and specs show a disciplined development process. The yaks themselves (`.yaks/`) serve as a living backlog — dogfooding the tool.

### 5. Developer Experience Infrastructure

Mutation testing (`cargo-mutants`) with missed mutants tracked as yaks. Pre-commit hooks. `dev check` as a single quality gate. Nix-based reproducible development environment. Shell completions. This is the infrastructure of someone who values sustained velocity.

## Concerns

### 1. `main.rs` is 657 lines and violating its own ADR

ADR 0008 says "keep main.rs thin: only wiring and routing." The `Commands::Reset` arm alone is ~80 lines of business logic including topological traversal, event replay, and schema version stamping. The `Commands::Context` and `Commands::Field` arms contain editor-launching logic and conditional stdin handling. The `Commands::Compact` arm does sync, confirmation prompting, and reporting.

**Recommendation:** Extract `ResetYaks`, `CompactYaks` use cases. Move the editor/stdin resolution logic out of main into the relevant use cases or a shared input-resolution helper. This is the single most impactful cleanup.

### 2. YakMap is an aggregate that loads from the read model

`YakMap::from_store()` reconstitutes the aggregate from the read model (the projected `.yaks/` directory), not from the event store. This is acknowledged in ADR 0002 as "effectively loading from a snapshot." While pragmatic, it creates a subtle inconsistency: the aggregate — which is supposed to be the source of truth for invariants — is built from the projection, which is a derived view.

Today this is fine because the projection is synchronous. But it means:
- If the projection has a bug, the aggregate loads corrupt state
- There's no sequence number linking the read model to the event store
- The `from_store` method has no awareness of which events have been applied

This isn't a crisis, but it's worth understanding the trade-off. The aggregate is not truly event-sourced; it's snapshot-sourced from a projected view.

### 3. Step definition duplication across worlds

Every step in `steps.rs` is defined twice — once for `FullStackWorld`, once for `InProcessWorld`. This is ~1,800 lines of largely duplicated step definitions. The `TestWorld` trait was introduced to share implementation, but Cucumber-rs requires concrete type registration per step. This is a framework limitation, not a design flaw, but it's a maintenance burden.

**Recommendation:** Consider whether a macro could generate the duplicate registrations, or whether the in-process world could be made the default (faster test feedback) with a smaller set of full-stack smoke tests.

### 4. The `Yak` struct has public fields and no behavior

`Yak` is essentially a data bag with `pub` fields and a single `is_done()` method. All business logic lives in `YakMap`. This is a design choice (anemic entity vs. rich aggregate), and it's defensible — `Yak` is a read-model DTO, not a domain entity. But the naming is confusing: `Yak` sounds like the domain concept, while `YakState` (the actual YakMap internal) is the richer type but it's `pub(crate)`.

**Recommendation:** Consider renaming `Yak` to `YakView` or `YakSnapshot` (oh wait, `YakSnapshot` already exists for compaction). At minimum, document that `Yak` is a read-model projection, not the domain entity.

### 5. Git adapter complexity

`git.rs` (1,862 lines) and `directory.rs` (1,270 lines) are the largest files and the most complex. The git event store handles tree serialization, sync with CRDT merge, compaction, and migration. This is necessary complexity, but it's tightly coupled — sync is an event store responsibility per ADR 0007, which means the git adapter does persistence, networking, and conflict resolution all in one type.

**Recommendation:** Consider splitting `GitEventStore` into smaller internal modules: tree serialization, sync protocol, merge strategy. The public interface stays the same; the internals become more navigable.

### 6. No aggregate-level invariant enforcement for concurrent access

The YakMap loads state, validates, emits events, then appends. There's no optimistic concurrency check (e.g., "append only if the stream is at version N"). In practice this is safe because `yx` is a CLI tool that runs sequentially, and sync uses CRDT merge. But if two processes ever run simultaneously against the same repo, events could be appended based on stale state.

This is fine for now but worth noting as a structural limitation.

## Minor Observations

- **Event format is text-based** (`Added: "name" "id"`), which is simple and human-readable but fragile. The parsing with `parse_quoted_values` handles edge cases but a structured format (JSON lines) would be more robust for evolution.
- **`DefaultHasher` for ID generation** — the docs warn this is not guaranteed stable across Rust versions. If IDs ever need to be reproducible across compiler versions, consider a stable hash like FNV or xxHash.
- **The `UseCase` trait** is effectively a command pattern, which is clean. But `AddYak` implements `execute` both as an inherent method and a trait method (the trait just delegates). This double-impl is a minor wart.
- **`InMemoryStorage` uses `RefCell<HashMap>`** which panics on concurrent access. Fine for tests, but the pattern could bite in async test contexts.

## Overall Grade

| Dimension | Rating | Notes |
|-----------|--------|-------|
| **Maintainability** | ★★★★☆ | Clean architecture, good separation. Main.rs bloat is the main drag. |
| **Habitability** | ★★★★★ | ADRs, READMEs, clear naming, dogfooded backlog. A new developer would know where to start. |
| **Legibility** | ★★★★☆ | Rust is readable, feature files are excellent. Step duplication and large adapters reduce navigability. |
| **Test Quality** | ★★★★★ | BDD + unit + contract + mutation testing. Dual-world execution. This is the standout. |
| **Architecture Fit** | ★★★★☆ | CQRS/ES is heavy for a TODO list, but applied thoughtfully with clear justification. |

**Bottom line:** This is a well-crafted codebase built by someone who knows what they're doing. The architecture is ambitious for the problem size but serves real goals (sync, audit, testability). The main risks are maintenance burden from the dual-world tests and the growing `main.rs`. Neither is structural.
