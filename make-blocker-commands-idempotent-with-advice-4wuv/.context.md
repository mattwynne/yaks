# Goal

Make explicit blocker add/remove commands safe to repeat, with helpful advice and no duplicate events.

# Scope

Focus on command semantics for duplicate, absent, and hierarchy-redundant explicit blocker operations. Do not implement general cycle detection or move validation here except as needed to preserve existing behaviour.

# Rules / Examples

## Duplicate adds are no-op successes unless the reason changes

```gherkin
Scenario: Adding an already active blocker with no change
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug"
  And I run yx blocker add deploy --by "fix bug"
  When I run yx blocker add deploy --by "fix bug"
  Then the command should succeed
  And the output should advise that "fix bug" already blocks "deploy"
  And the log should not include a new BlockerAdded event for "deploy" blocked by "fix bug"
```

```gherkin
Scenario: Adding an already active blocker with the same reason
  Given "deploy" is explicitly blocked by "fix bug" with reason "crashes in staging"
  When I run yx blocker add deploy --by "fix bug" --reason "crashes in staging"
  Then the command should succeed
  And the output should advise that nothing changed
  And the log should not include a new blocker event
```

```gherkin
Scenario: Changing the reason for an active blocker
  Given "deploy" is explicitly blocked by "fix bug" with reason "crashes in staging"
  When I run yx blocker add deploy --by "fix bug" --reason "crashes in prod"
  Then the command should succeed
  And the log should include a BlockerUpdated event for "deploy" blocked by "fix bug"
  And "deploy" should be blocked by "fix bug" with reason "crashes in prod"
```

## Absent removes are no-op successes

```gherkin
Scenario: Removing a blocker that is not active
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug"
  When I run yx blocker rm deploy --by "fix bug"
  Then the command should succeed
  And the output should advise that no such blocker was active
  And the log should not include a BlockerRemoved event for "deploy" blocked by "fix bug"
```

## Hierarchy-redundant blockers are no-op successes

Hierarchy already makes descendants block ancestors, so adding the same relationship explicitly is redundant.

```gherkin
Scenario: Adding an explicit blocker already implied by hierarchy
  Given I have a clean git repository
  And I add the yak "deploy"
  And I add the yak "fix bug" under "deploy"
  When I run yx blocker add deploy --by "fix bug"
  Then the command should succeed
  And the output should advise that "fix bug" already blocks "deploy" through hierarchy
  And the log should not include a BlockerAdded event
```

# Acceptance Notes

- Re-running blocker commands should be safe in scripts.
- No duplicate `BlockerAdded` / `BlockerRemoved` events are emitted for no-op operations.
- Changed reasons still emit `BlockerUpdated`.
- Advice should be human-readable but tests should assert key information rather than brittle full prose.
- JSON readiness/blocked_by semantics from the previous vertical slice must remain unchanged.

# Test Guidance

Use Gherkin for the visible CLI behaviour and event-log expectations. Add focused unit tests only if helpful around projection/idempotency helpers.
