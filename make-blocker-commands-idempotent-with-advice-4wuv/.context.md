# Goal

Make blocker add/remove commands idempotent and helpful.

# Rules

- Adding an already-active explicit blocker with no effective change succeeds, emits no event, and prints advice.
- Adding an already-active explicit blocker with the same reason succeeds, emits no event, and prints advice.
- Adding an existing blocker with a changed reason emits `BlockerUpdated`.
- Adding an explicit blocker already implied by hierarchy succeeds as a no-op, emits no event, and advises that hierarchy already provides the blocker.
- Removing an absent explicit blocker succeeds as a no-op, emits no event, and prints advice.

# Examples / BDD

## Duplicate add with no change

Given `A` is explicitly blocked by `B`
When I run `yx blocker add A --by B`
Then the command succeeds
And the output advises that `B` already blocks `A`
And no new blocker event is emitted.

## Duplicate add with same reason

Given `A` is explicitly blocked by `B` with reason `x`
When I run `yx blocker add A --by B --reason x`
Then the command succeeds
And the output advises that nothing changed
And no new blocker event is emitted.

## Duplicate add with changed reason

Given `A` is explicitly blocked by `B` with reason `x`
When I run `yx blocker add A --by B --reason y`
Then `BlockerUpdated(A, B, y)` is emitted.

## Absent remove

Given `A` is not explicitly blocked by `B`
When I run `yx blocker rm A --by B`
Then the command succeeds
And the output advises that no such blocker was active
And no event is emitted.

## Redundant hierarchy blocker

Given `child` is under `parent`
When I run `yx blocker add parent --by child`
Then the command succeeds
And the output advises that `child` already blocks `parent` through hierarchy
And no explicit blocker event is emitted.

# Test Guidance

Prefer Gherkin for command-visible behaviour. Assert log output or event count where practical so no-op cases cannot silently emit duplicate events.
